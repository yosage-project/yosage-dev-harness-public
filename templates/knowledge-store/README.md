# 知識ストア

組織のすべてのプロジェクトで共有する知識(グローバルな知識)を置く、独立した git リポジトリ。
Claude Code のプラグイン `yosage-dev-harness` が、各プロジェクトのセッションの開始時にここを読み取り専用の
写しとして受け取る。この中身は、**自分の組織に合わせて書き換えて使う雛形**から始まっている。
書き換える箇所は、下の「この雛形を自分の組織に合わせる」を見る。

合わせたハーネスの版: @HARNESS_VERSION@

## ここに置くもの

- `knowledge/<ドメイン>/*.md` … 知識のエントリ。1件に1つのルールと、その理由。
- `review/criteria.md` … 組織が足していくレビュー観点。基本の観点はハーネスが持つので、ここは組織の分だけ。
- `README.md`・`LICENSE` … ストアの説明と、使ってよい条件。同期では読まれない(ストアに置かれるだけ)。

ディレクトリの形・ファイル名・エントリの項目の約束は、ハーネスの
[`docs/knowledge.md`](@HARNESS_DOCS_URL@) の「共有ストアを設定する」にある。ここには書き写さない
(ここを書き換えても、約束はそちらを正とする)。

## 使い方

1. このストアを、プロジェクトから指す。プロジェクトの `.claude/yosage-dev-harness.local.json`
   (git で追跡しない)に書く:

   ```json
   {
     "knowledge": {
       "enabled": true,
       "source": "<このストアの URL>",
       "ref": "main"
     }
   }
   ```

2. 各プロジェクトで作業すると、学びがそのプロジェクトの `.claude/knowledge/` にたまる。
   全プロジェクトで成り立つと判断したものに `scope: global` の印が付く。
3. ある程度たまったら、人が `/yosage-dev-harness:promote-knowledge` を実行する。候補を精査し、
   このストアへ**昇格の PR** を出す。
4. **人がその PR をレビューして、マージする。** これが唯一の関門で、自動ではマージされない。
5. マージされると、次のセッションの開始時に、すべてのプロジェクトへ写しが届く。

## ブランチとマージ

- 既定のブランチは `main`。変更は PR で出し、直接 push しない。
- マージは**マージコミット**で行う(squash しない・rebase しない)。
- リリースのタグは切らない。知識は積み増しで、`main` に追従する。

## 越えない線

- **正本は git のテキスト。** データベースや外部サービスに正本を置かない。
- **客先や他社の知識を、ここへ集めない。** 置くのは、自分の組織の内部で、どのプロジェクトでも成り立つ
  汎用の知識だけ。案件に固有のものは、その案件のリポジトリに残す。
- **自動で全体に効かせない。** プロジェクトからここへの昇格は、必ず人がレビューする PR を通す。
- **ほかのリポジトリへの参照を持ち込まない。** issue や PR の番号、非公開のリポジトリ名、社内ツールの名前は
  書かない。エントリは、これだけ読んで意味が通る形にする。

## 形を確かめる

ハーネスの実行ファイルで、このストアの形を確かめられる。違反があれば一覧を出し、終了コードが 0 以外になる。

```bash
yosage-dev-harness-knowledge-store-check .
```

## この雛形を自分の組織に合わせる

- リポジトリ名は自由に付けてよい(例: `<組織名>-knowledge`)。ハーネスはリポジトリの名前を見ない
  (取得は `knowledge.source` の URL と `knowledge.ref` で行い、中身は上の「ここに置くもの」に従う)。
- この README を、自分の組織の運用に合わせて書き換える。「合わせたハーネスの版」の行は、雛形を作った
  時点の版の記録なので、消してよい。
- エントリの書き方は、ハーネスの `docs/knowledge.md` と、書き出し用の雛形を出す
  `yosage-dev-harness-knowledge-template` を見る。この雛形には見本のエントリを置いていない
  (置くと、消し忘れが同期で全プロジェクトに配られるため)。`knowledge/` は、最初の昇格 PR で埋まる。
- `review/criteria.md` も、役割の説明だけを置いている。組織の観点が入ったら、説明を残すか消すかは自由。
- `LICENSE` は、この雛形そのものを使ってよい条件。ストアの中身をどの条件で扱うかは、組織の方針で決めて差し替える。
