# センシティブデータ取り扱い（不変条件）

認証 secret・PII・組織境界の識別子（自組織の org 名・repo 名・内部ツール名等）を durable 成果物
（git 追跡物・issue/PR・knowledge・memory・docs）へ**漏らさない**ための正本である。防御の主線は
**commit 前**とされている（PR レビューでは遅い）。no-squash 運用では、一度コミットした秘密はマージ後も
履歴に永久に残る。組織境界の識別子は commit ではなく**外向きの投稿**（issue/PR/コメント）が
主な漏出経路であり、扱いは下記「別トラック方針」の対応行を参照。

## 検査の指示に検査対象を書かない（一般形）

「これが混入していないか確認せよ」と、確認したい対象そのもの（secret の値・禁止語・組織の
識別子）を指示に書いて渡すと、**指示を受けた側がその対象を報告文へ書き写し、そのまま durable
成果物へ投稿してしまう**。検査を依頼する指示そのものが検査対象を書かせる、という事故の型である。

この形の混入は下記②の自己チェックを素通りする。書いた本人の意識では「対象が無いことを確認
した」であって「対象を書いた」ではないため、書き込み前の自問（この文はセッション外の読者に
通じるか／禁止事項に触れていないか）が発火しない。

- **確認の指示は抽象で書くことになっている**。確認してほしい対象の値そのものは渡さず、性質・分類名で指示することになっている。
  - ✗「この secret（`<値>`）が混入していないか確認せよ」 → ✓「secret が混入していないか確認せよ」
  - ✗「自組織の識別子（`<org 名>` / `<repo 名>`）が混入していないか確認せよ」
    → ✓「投稿先で禁止された自組織の識別子が混入していないか確認せよ」
- **報告の書式にも対象を書かせない**決まりになっている。「検索したが該当なし」という報告文自体に対象を書き写す
  経路も同型なので、報告に対象の値を含めない指示にすることになっている。
- 対象は secret・PII に限らない。「別の宛先では不適切になる値」全般（組織境界の識別子を含む）
  に同じ事故の型が起きる。

## ① 置き場

センシティブな値（認証 secret・API キー・PII）は durable 成果物に**書かない**決まりになっている。

- durable 成果物 = git 追跡物 / issue・PR 本文 / knowledge エントリ / memory / docs
- 運用で要る値は **gitignore された定位置**（`*.local.*` 流儀の拡張）へ置くことになっている。
  例: `.claude/yosage-dev-harness.local.json`（同期 source・通知 webhook URL 等）。
- gitignore の機構面は `.gitignore` が担う。秘密ファイルの Read ツール経由の読み取りは、推奨設定の見本（`permissions.deny`。利用者が自分の `.claude/settings.json` へ採る）で塞ぐことになっている。実行コマンドのフックは `guard.sh` が担う（本ルールはポリシーの正本）。

## ② commit 前の自己チェック（主体が in-context で行う）

主体は `git commit` を実行する**前**に staged diff（`git diff --staged`）を secret/PII 観点でスイープすることになっている。

- **secret を見つけた場合**: コミットせず、gitignore された定位置へ退避するか redact することになっている。
- **PII を見つけた場合**: コミットせず、必要性を判断した上で redact または gitignore 先へ退避することになっている。
- **判断に迷う場合**: コミットせず、理由を添えて人へエスカレーションすることになっている（黙っては通さない）。
- チェックは **in-context** で行うことになっている（別 agent を spawn しない）。
- 機械的ガードはセッション内のガード（`git commit` の時点でステージした内容を読む）が担う（本ルールはポリシーの正本）。ハーネスが止めるのは Claude の操作だけであり、人がエディタ・別ターミナルで行うコミットは範囲外である（使う人が gitleaks 等で自衛する領域）。

## ③ 保護の適用範囲（どのリポジトリに・どこまで効くか）

機械的ガード（`guard.sh`）は **`git commit` の時点で対象リポジトリの staged 内容を実際に読み取って走査する**。ワークスペース運用（複数リポジトリが同居し、同一セッションが子リポジトリ・member リポジトリ（他社所有を含む）へも `git commit` する構成）でも、このセッションの Bash 経由であれば対象になる。

- **効かない範囲**: エディタ・別ターミナル等、このセッションを経由しないコミットは見えない。ハーネスが止めるのは Claude の操作だけである。

## 別トラック方針（検出手段の違い）

| 種別 | 検出手段 | 安全網 |
|---|---|---|
| secret（認証トークン・API キー等） | 決定論的パターン（`guard.sh`）  | 機械ガード＋主体の目視確認 |
| 自由記述 PII（氏名・住所等） | 機械判定不可 | 主体判断＋`yosage-dev-harness:code-reviewer` の観点（セキュリティの「durable な成果物への混入」）でのレビュー |
| 組織境界の識別子（org 名・repo 名・内部ツール名） | **宛先依存**（同じ語が自組織の宛先では正当・他組織の宛先では不適切になるため、secret のような単一の禁止パターンでは判定できない） | 上記「検査の指示に検査対象を書かない」＋**外向きの投稿を扱う共通ライブラリでの警告**（下記） |

秘密ファイルの読み取り（`.env` 系・`*.pem`・`*.key`・`id_rsa`・`secrets/**` 等）は、Read・Grep・Bash（cat/grep/head/tail/less/find 等）のいずれの経路でもガードが止めることになっている（`lib/secret-patterns.sh` の `sf_is_secret_path` が唯一の判定元）。

自由記述 PII は regex では取りきれない。主体が staged diff を読んで判断することになっており、`yosage-dev-harness:code-reviewer` が安全網として機能する。

### 組織境界の識別子: ブロックせず警告する（設定ファイルを持たない）

組織境界の識別子は secret と違い、値そのものを一意に禁止できない（自組織の宛先では書いて
正当な語が、他組織の宛先では不適切になる）。**判定には宛先ごとの禁止語リストが要るように見えるが、
その値自体が識別子であるため追跡管理できる場所に置けない**（追跡すれば識別子を配布物へ焼き込む
ことになり、追跡しなければ設定を持つ環境ごとに有無がバラつく＝最も要る場面で確実に効かない）。

このため機械的な安全網は次の設計になっている。

- **ブロックしない・警告のみ**（作業を止めない）。ブロックには判定の正確さが要求されるが、
  正確さのための設定ファイルは持てない、という制約への対応である。警告なら誤検知が安くて済むので、
  設定は持たず**投稿先リポジトリと、ワークスペースに同居しているリポジトリの owner/repo 名を
  git remote から動的に導出**して判定することになっている（設定忘れ・環境ごとの有無のばらつきが原理的に起きない）。
- **投稿の直前に警告する**（事後ではなく、通知が飛ぶ前に気づける位置）。外向きの投稿を扱う
  共通ライブラリ（`gh-review.sh`）の review/reply 投稿の直前に置くことになっている。
- **一致した語そのものをメッセージには出さない**決まりになっている。出すと、その出力が別の durable 成果物へ
  転記されうる（上記「検査の指示に検査対象を書かない」と同じ事故の形）。宛先と件数までに留めることになっている。
