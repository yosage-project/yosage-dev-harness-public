# 割り当て作業ツリーの置き場（不変条件）

割り当て作業ツリー（`isolation:"worktree"` が作るもの、または cross-repo 構成でメインが明示的に
`git worktree add` するもの）の置き場は、**対象リポジトリの `.claude/worktrees/<id>` 配下**に固定されている。

この置き場は単一ホーム（ハーネスの `lib/worktree-root.sh`）が
持つ値であり、次の2箇所が同じ値を参照することになっている。**片方だけを変えると発火・掃除のどちらかが揃わなくなる。**

- **遮断の判定**（`hooks/guard.sh`）: hook 入力の `.cwd` がこの配下のときだけ、worktree 隔離
  サブエージェントの逸脱検知（共有チェックアウト外への書き込み・git 操作）が発火する。配下でなければ
  no-op のまま素通しになる（通常のメインセッションを誤爆させないための意図的な設計であり、本条項が
  変えるものではない）。
- **掃除の走査**（`lib/epic-cleanup.sh`）: 走査範囲の既定値はこの配下に固定されている。配下でなければ、
  掃除は該当する作業ツリーを黙って見逃す（エラーにはならない）。

**cross-repo 構成でメインが明示的に `git worktree add <絶対パス> <branch>` する場合も同じ制約が
掛かる**（[[epic-implement]] の cross-repo 代替手順）。`<絶対パス>` は必ず対象リポジトリの
`.claude/worktrees/<id>` 配下を選ぶことになっている。ここを外すと、その作業ツリーに対して遮断は発火せず、
掃除も黙って見逃す。この `git worktree add` の前には `yosage-dev-harness-ensure-worktrees-ignore
<対象リポジトリのルート>` を実行し、`.claude/worktrees/.gitignore` を用意しておく（[[epic-implement]]
の cross-repo 代替手順1を参照。本節では再記述しない）。

## この不変条件は規律で受ける（機械的な強制は持たない）

cross-repo の `git worktree add` はメインが対話的に絶対パスを選ぶ操作であり、実行前にその絶対パスを
検査して弾く機構はここでは持たない（遮断の判定そのものの発火条件を広げる設計変更は本ルールの対象外である）。
掃除の走査範囲から外れた作業ツリーが黙って残る挙動についても、同じ理由でここでは直さない——
`lib/epic-cleanup.sh` の既定の走査範囲は変えず、置き場を本ルールで縛ることで防ぐ側に倒している。

## そもそも隔離されなかった作業者は、本ルールでは検知できない（既知の限界）

上記の遮断・掃除は、いずれも hook 入力の `.cwd` が割り当て作業ツリー配下であることを前提に発火する。
`isolation:"worktree"` が要求されたのに実際には作業ツリーが用意されず、作業者の `.cwd` が最初から
共有チェックアウトそのものである場合、この前提そのものが成立しないため、遮断・掃除のどちらも発火しない
（作業者は外形上、通常のメインセッションと区別がつかない）。

この状態を外形（環境変数・hook 入力の追加フィールド）から判定できるかを調査した結果は次のとおりである。PreToolUse hook
入力が実際に持つフィールドは `cwd` / `tool_input.*` / `session_id` / `hook_event_name` に限られ
（既存 hooks が実際に消費しているフィールドを横断的に確認した）、サブエージェントの種別や
`isolation` 指定の有無を示すフィールドは無い。環境変数側では、サブエージェント（Task 起動）セッション
であることを示す値を1つ実機で確認できたが、これは「メインかサブエージェントか」しか示さず、
「隔離されるべきサブエージェント種別か、隔離不要な種別（レビュー系等・読み取り中心で worktree を
要しない）か」までは区別できない——後者は前者の判定に必要な情報を持たない。

加えて、hook 側で（block ではなく）非ブロッキングの警告を足しても、書き込みを行った当のエージェント
自身には届くとは限らない（本ファイルが参照する `hooks/guard.sh` 自身の既存設計: 届くのは exit 2 の
場合に限られ、exit 0 の stderr が Claude に届くという前提は無い）。ブロック（exit 2）にするには、
上記の不完全な信号のままでは誤検知（隔離不要な作業を止める）を排除しきれない。

したがって**外形からの機構的な検知は採らず**、worktree 隔離を要求されるサブエージェント定義
（`agents/implementer.md`・`agents/test-writer.md`）側に、着手直後に `.cwd` が割り当て作業ツリー
配下かを自己確認し、そうでなければ自分で復旧せず報告して停止することになっている、という規律を明文化する対処に倒した。

## 反証条件

- **cross-repo 経路そのものが無くなった場合**（作業ツリーの用意が常に `isolation` 経由の自動配置に
  寄った場合） — 本ルールの制約は不要になる（`isolation` 経由は既にこの置き場を使うため）。
- **単一ホームの値を変えても判定側・掃除側の両方が追随しない場合が見つかった場合** — 集約が崩れて
  いるので、`lib/worktree-root.sh` の参照箇所を洗い直すことになる。
- **掃除が黙って見逃す挙動が実害を繰り返した場合** — 規律だけで受ける判断を見直し、機械的な検知
  （例: 走査範囲外に取り残された worktree を警告する）を検討することになる。
- **呼び出し元セッションが `isolation:"worktree"` を指定されていたかを判別できるフィールドが、
  hook 入力または環境変数として将来得られるようになった場合** — 上記「そもそも隔離されなかった
  作業者は、本ルールでは検知できない」の前提が崩れるので、機構的な検知（本ルールの遮断発火条件の
  拡張）を再検討することになる。
- **上記の自己確認（`agents/implementer.md`・`agents/test-writer.md` の着手直後の cwd 確認）に
  頼る対処を採ったのちに、実際に不可逆な操作（共有チェックアウト側への書き込み・コミット・
  ブランチ操作等）が起きた場合** — 「機構的検知を見送り、自己確認の明文化と報告で被害を防ぐ」
  という判断が前提にしていた「指示を足せば被害は防げる」という見立てが崩れたことになる。
  この場合は本節の判断を単独では維持せず、機構的な防止（本ルールの遮断発火条件の拡張、または
  対象を絞ったブロックの追加）へ倒すことになる。
