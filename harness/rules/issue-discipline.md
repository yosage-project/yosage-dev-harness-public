# issue 規律（不変条件）

actionable は issue に一元化することになっており、**「issue を見れば対応できる」**状態が保たれている。

## self-contained
- 全 issue は self-contained とする決まりになっている＝**背景・受け入れ条件をインライン**、種別ラベル、耐久リンクのみ。
- Sub-issue だけでなく**単発 issue にも適用される**。
- PR 本文も同様に **repo 内で自己完結**させることになっている。

### 文脈的自己完結（セッション内符牒の禁止）
- セッション内符牒（「案A」「OQ3」「さっき決めた方針」等、形は可変＝`案A'`・`方針B` 等の派生も同様）は**そのまま書かず中身に展開する**決まりになっている。
- 判定基準:「**そのセッションに居なかったチームメンバーが、この文だけで対応できるか？**」No なら符牒を中身に置き換えることになっている。
- 例: ✗「案A を採用」→ ✓「メインは実装せず yosage-dev-harness:implementer に dispatch する方針を採用」
- **適用範囲**: issue / PR 本文に限らず durable な成果物全般（**コードコメント・knowledge を含む**）に加え、
  **人へ判断を求める提示**（`AskUserQuestion` 等の会話上の質問）**にも適用される**（durable ではないが、
  判断を求める場で符牒のまま出すと相手が判断できないため）。記号の使用自体は禁止されていない——禁止されるのは
  「記号のまま判断を求めること」であり、判断を求める時点で中身に展開するか、記号と中身の対応表を添えることになっている。
  - **反証条件**: 展開により提示が長くなり読まれなくなった場合は「対応表を1つ添える」形へ絞ることになっている。人が
    記号のままで問題なく判断できている場合（短い討議・当日中に閉じる議論等）は、適用範囲を
    「セッションをまたぐ提示」に絞ることになっている。
- **コードコメントの扱い**: 符牒は禁止されている。経緯は issue 番号で耐久リンクとする決まりになっている（例: `// 背景: #<issue>`）。本文に経緯は長文展開しない。
  - **carve-out（配布 payload）**: 上記の `#N` 耐久リンクは同一 repo 内で読まれる前提。**consumer 自身の repo 内コード**のコメントは `#N` 可（same-repo で解決）。**配布 payload のコメント**（他 repo へ配布・travel するコード）は source-repo の `#N` を載せない決まりになっている。経緯は実体説明＋耐久リンク（外部 URL 等）で表すことになっている（travel 面の自己完結は ルール `knowledge` の `## 書き方不変: travel 面の自己完結` と同一メタ原則）。
- **防御の主線: 起票／書き込み前の主体 in-context 自己チェック**: durable 成果物（issue/PR 本文・コードコメント等）へ**書き込む前**に、書く主体が上の判定基準（そのセッションに居なかったチームメンバーが、この文だけで対応できるか？）を自問し、符牒を展開したかをその場でチェックすることになっている。ルール `sensitive-data` の「② commit 前の自己チェック（主体が in-context で行う）」と同型の位置づけである（同ファイルの中身は再記述しない）。
- **検出は独立した安全網（2層の補完）**: yosage-dev-harness:consistency-reviewer の「文脈外参照」観点は、書き込み前の自己チェックを補う**独立したレビュー層**として維持されている（書き込み前の早い自己捕捉＋独立レビューによる盲点補正、の2層の補完）。機械的な正規表現ガードは入れないことになっている。
  - **この第2層は「人へ判断を求める提示」には届かない**: 第2層は durable 成果物を走査対象にするが、
    上記「人へ判断を求める提示」は会話の出力であり durable ではないため、構造的に対象外になる。
    **この提示については第1層（書き込み前の自己チェック）だけで受けると判断している**——見落としで
    対象外なのではなく、判断してそう決めている。
  - **「人へ判断を求める提示」のうち判断そのものを求めるものは durable な記録を伴う**: 対象は
    blocking OQ・価値トレードオフ判断など、実質的な判断を求める提示に限る（**軽い確認・往復は対象外**
    ——含めると摩擦になるため）。判断を求める前に、その内容を issue・PR コメント等の durable な
    記録として残す。この記録は上記の独立レビュー層の対象になるため、**この部分集合に限り第2層が
    間接的に届く**。

## 起票前の重複確認
actionable を新規 issue にする前に、**同じ内容の issue が既に無いかを検索する**決まりになっている。検索を省略した起票は
本規律違反として扱われる（本文が self-contained でも、重複そのものは防げない）。

- **対象範囲**: open だけでなく **closed も検索対象に含める**ことになっている（`gh issue list --search "<語>" --state all`）。
  対応済み/放置のまま閉じられた issue との重複は open だけを見ていては検出できない
  （監査以前から存在していた issue との重複、が実例）。
- **検索語**: タイトルの主要語・関連するファイル/コンポーネント名など、複数の言い回しで引くことになっている。
  1語で「無い」と即断しない決まりになっている。
- **見つかった場合の扱い**:
  - **同一の問題**（対応すれば両方解消する）→ 新規には起票せず、既存 issue へ追記することになっている
    （コメント or 本文更新。クローズ済みなら再発/未解消である旨を明記して再オープンを判断する）。
  - **別物と判断する場合**（関連はあるが対応すべき事柄が異なる）→ 新規に起票してよいが、
    **判断根拠**（何が違うか）と既存 issue への言及（耐久リンク）を新規 issue の本文に残すことになっている。
- **検索したこと自体を前提の手順とする**: 「見つからなかった」という結果だけでなく、起票前に検索を
  行うこと自体が手順の一部として位置づけられている（結果に関わらず省略しない）。

**置き場について**: issue を作る主体は起票側（実装フラクタル）だけでなく、要件を issue へ落とし込む
統制側にも及ぶ。置き場は消費者が広い側（本規律）に統一することになっており、統制側の要件取り込み手順は本規律を
名前参照する形に留めることになっている（ここへ追加すれば自動的にカバーされ、統制側での再記述は不要になる）。

## repo 外参照を禁止
- 上位ディレクトリ参照やワークスペース絶対パスは GitHub 上で壊れる（複数リポジトリのワークスペースで届かない）。
- 横断/一時 doc の**内容はインライン展開**し、リンクが要るなら**耐久 URL**（共有 issue / wiki / drive）を使うことになっている。

## doc に作業を埋めない
- 設計・計画 doc で対応すべき事項が出たら **issue を生やしてリンク**することになっている（doc 側は issue 番号を残す）。
- 検討中の設計は doc にメモらず issue で議論することになっている（置き場の詳細は [doc-placement](doc-placement.md)）。
