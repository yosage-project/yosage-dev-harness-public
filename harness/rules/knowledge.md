# knowledge loop（不変条件）

学びは腐らせず蓄積し、繰り返す問題はルール/観点へ昇格させる運用になっている。**読む＝recall（前）／書く＝capture（後）**。

## 主体が loop を持つ（責務の所在）
**その作業をした主体が recall（前）→ capture（後）を回すことになっている。**
- メイン（オーケストレーター）が**設計・統制**したら → **メインが回す**（別主体には投げない。実装は `yosage-dev-harness:implementer` に dispatch＝正本 `implement-routing`、その yosage-dev-harness:implementer が回すことになっている）。
- `yosage-dev-harness:implementer` サブエージェントが実装したら → **そのサブエージェントが回す**（worker＝in-context なので内蔵で正しい）。
- 「全部サブエージェントに寄せる」必要はない。要点は **主体が loop を持つ**ことにある。**メイン直（設計・統制）の道でも省かれない**。

## recall（前）/ capture（後）
- **recall（前）**: 着手前に既存知見を引くことになっている＝[[recall-knowledge]]（既定で `yosage-dev-harness:librarian` に委譲）。設計の接地は [[grounded-design]]。
- **capture（後）**: 一段落ごとに学びを残すことになっている＝[[capture-learning]]。**in-context の skill**（専用 subagent には投げない＝作業の文脈が要るため）。
- **捕捉すべき学びが無ければ「無し」と判断してよい**（ただし振り返らず素通しにはしない＝判断はする決まりになっている）。
- **fix-on-recall**: recall 時に既存知見の腐り（参照が実体と合わない／教訓が覆った）を検出したら、その場で主体が直すことになっている＝capture の一形態（[[capture-learning]]）。検出（`yosage-dev-harness:librarian`・read-only）と修復（主体）は分離される。
- **promote-on-recall**: recall 時に `yosage-dev-harness:librarian` が昇格適性も判定し、強い候補を digest に flag する（read-only）。主体がそれを見て、未マークなら `scope: global` staging マークを、既にマーク済みなら明示実行の `promote-knowledge`（別スキル）を実行することになっている＝capture の一形態（[[capture-learning]]）。fix-on-recall と同型：検出（`yosage-dev-harness:librarian`・read-only）と行為（主体）は分離される。
- **外部 just-in-time**: 内部知見だけで足りないときは外部（言語定石・公式 doc・原理原則）を `yosage-dev-harness:researcher` で引くのも recall の一形態である（引く条件・確立済み/新規での濃淡は [[recall-knowledge]]）。残すのは base model への差分だけ＝価値ゲート（[[capture-learning]]）。モデルが持つ一般論は引かない・残さない決まりになっている（過信 recall を量で再発させない）。

## ローカル索引は任意のキャッシュ（廃止・エントリの直接列挙のみ）
project-local の `.claude/knowledge/INDEX.md` / `INDEX.archive.md` は**生成しない**決まりになっている
（ローカル索引は廃止済み。project-local ストアの置き場は `.claude/knowledge` に固定されている——置き場を
変える機能は撤去済み）。recall は**エントリの直接列挙**（`yosage-dev-harness-knowledge-index
.claude/knowledge --list [domain]` ＝現行のみ／`--list-archive` ＝現行外も同様に列挙）だけを経路とする。

- **なぜ**: 索引はエントリ frontmatter から機械的に再生成できる派生物にすぎないが、複数ブランチが並行してエントリを
  追加すると、集約物である索引ファイルだけが textual に衝突する（内容の対立ではなく形式上の衝突。解決は
  再生成だけだが、並行度が上がるほど頻発する）。加えて、追跡されると「正本らしく」見え、手編集で
  ずれる余地が構造的に残る。**索引が買っている絞り込みの速さは、今の規模ではまだ便益が発生していない
  最適化**であり、そのために上記の実害を先払いする理由がない。
- **同じ結果になる保証**: `--list`/`--list-archive` は書き出しモードと**同じ解析・フィルタコード**
  （`yosage-dev-harness:lib/knowledge-index.sh`）を使い回す。索引を生成した場合の内容と、直接列挙した場合の内容は
  構造的に一致する（別の解析器を持たないので drift しない）。
- **生成器は検証器として残す**: 既定（引数無し）の書き出しモードは**グローバル側**（下記）のために維持する。
  project-local への書き込み時フックは検証だけのモード（`--check`。ファイルを書かない）で生成器を呼び、
  宣言部（frontmatter）の書式検証（壊れた `summary` の検出等）だけを効かせる。
- **グローバル側は非対称**: `.claude/knowledge/global/INDEX.md` は同期時に生成される索引を**維持する**
  （消費側は sync で受け取るだけの読み取り専用ミラーで、ローカルのような並行書き込み衝突が起きないため。
  差はここだけで、project-local の直接列挙の方針を変えるものではない）。
- **反証条件**（次のいずれかが観測されたら、project-local でも索引生成の復活を検討する）:
  1. 司書役が列挙する出力が実用上重くなった（文脈を圧迫する・応答が遅くなる）。
  2. project-local エントリ数が数百規模に達した。

### 列挙の失敗を「0件」と誤認しない
`knowledge-index.sh --list`/`--list-archive`（と構造監査 `knowledge-audit.sh`）は、結果を終了コードと出力の組で返す。
「0件」と「失敗」は次のとおり。

| 状況 | 終了コード | 意味 |
|---|---|---|
| `knowledge/` があり、該当エントリが0件 | 0（出力なし） | 該当エントリなし |
| `knowledge/` が無く、同じ `.claude/` に設定ファイル `yosage-dev-harness.local.json` がある（導入先） | 0（出力なし。監査は走査0件の1行を標準エラー出力へ） | 知見が0件（まだ1件も書いていない導入先） |
| `knowledge/` が無く設定ファイルも無い／`knowledge` がディレクトリでない／`.claude/` 自体が無い／権限が無い等 | 非ゼロ（`ki_log`／`return 1` を経由） | 失敗（引数の取り違え・位置解決の失敗の可能性） |

導入先で `knowledge/` が無いのを失敗にしないのは、空ディレクトリが git に残らず clone し直すと再び無くなるため。
設定ファイルで見分けるのは、位置解決の失敗まで0件にしないため。

実行主体は**終了コードを確認する**決まりになっており、非ゼロ終了を「関連知見なし」として先へは進まない——
ストアの位置解決に失敗した可能性として**その場で停止し、呼び出し元へ報告する**ことになっている。終了コード0かつ
出力が空の場合だけが「該当エントリなし（知見0件を含む）」を意味する。

## いつ capture するか
ユーザーに指摘・訂正された / レビューで同種の指摘が繰り返した / 「やってみて判明した」/ 設計を確定した / タスク完了の振り返り、が capture のタイミングとされている。

## 振り分け / 昇格（詳細手順は capture-learning）
- **ローカル（プロジェクト固有）＝直接書く** / **グローバル（全プロジェクト共通）＝既定はまずローカルに `scope: global` で staging**する決まりになっている（capture 時点では直接 PR しない）。
- **昇格は明示実行の `promote-knowledge`（別スキル）経由に一本化**することになっている（cross-repo・外向き着火は重い遷移＝人間トリガという [[design-routing]] / [[implement-routing]] の不変に整合。昇格は委譲対象外）。capture の場では判定・マークまでに留める。
- **昇格＝move（コピーではない）**: store にマージされたら**ローカルの昇格元 entry は削除**される（一般事実の家は store。固有の適用だけ別 `scope: local` で残す）。move 規則自体は既定反転の影響を受けない。
- 書き方（1件1ルール＋理由）・振り分け・昇格手順の詳細は [[capture-learning]] が、取得手順は [[recall-knowledge]] が持つ。

## 書き方不変: 引用照合ゲート（source: を持つ知見は原典と照合する）
`source:`（外部出典 URL）を持つ知見は、**原典を実際に開いて逐語で突き合わせて初めて「確認済み」**とみなされる。`source:` が付いていること自体は信頼の根拠にはならない（内部接地の `path` は grep で再解決でき腐りが検出できるが、外部出典は誰かが開き直さない限り検証されない非対称がある）。`source:` を持たない知見（内部接地＝`path` ＋ 安定ハンドルで grep 再解決できる）はこの節の対象外である。

- **安定ハンドルを要求する**: 知見が引用・見出し名・表名を挙げるなら、それらは原典から**再解決できる形**（見出し名・表名・逐語の引用）でなければならない決まりになっている。「公式ドキュメントに書いてある」のような曖昧な言及だけでは照合できないので、その時点で書き直しを求めることになっている。
- **原典を実際に開いて逐語で突き合わせる**: `source:` の URL を開き、知見が挙げる引用文言・見出し名・主張が原典に実在するかを確認することになっている。
  - **実行主体は主体 in-context が既定**（`source:` を持つ知見は全体で少数のため全件照合が軽い）。照合対象が多く隔離文脈が要ると判明した場合に限り subagent へ委譲してよい。
  - **委譲する場合、subagent の「確認した」という報告だけでは受理しない**決まりになっている。委譲先に**原典の逐語引用**を報告へ含めさせ、主体自身がその引用と主張を突き合わせることになっている。
- **`checked:` の意味**: `checked:` は**原典を開いて照合した日**を指す。未照合のまま日付だけを埋めることはしない。
- **結果で分岐する**（真偽軸の共通手順。着火点固有の帰結は各着火点の手順を参照）:
  - **一致**（引用・主張が原典に支持される）→ `checked:` を確認日（今日）へ更新することになっている。
  - **原典に無い主張・存在しない見出し名・存在しない引用**（原典は開けるが記述が見つからない）→ 記述を原典に合わせて訂正するか、支持されない記述を削るまで先へは進まない。**原典に無い主張を doc 由来として書かない**決まりになっている。
  - **原典と矛盾する主張**（原典の該当箇所がエントリと正反対のことを述べている）→ 止めることになっている。矛盾の内容（原典の該当箇所の引用 vs エントリの主張）を明らかにすることになっている。
  - **照合不能**（URL が到達不能・記述の有無が確認できない）→ 止めることになっている。到達不能である旨と試みた URL を残すことになっている。確認が取れるまで先へは進まず、原典に無い主張を doc 由来として書かない決まりになっている。
- **着火点固有の挙動は各着火点が持つ**（本節は真偽軸の共通手順のみを定める。「止める」を具体的に誰へどう伝えるか・いつ照合するかは着火点＝[[capture-learning]] / `promote-knowledge`（別スキル）側の責務とされている）。

## 書き方不変: 書き込み前の自己チェック（粒度混在・scope 妥当性）

知見を`.claude/knowledge/`へ**書き込む前**に、書く主体が in-context で次を自問することになっている。この位置づけは
[[issue-discipline]] の「防御の主線: 起票／書き込み前の主体 in-context 自己チェック」節・[[sensitive-data]]
の「② commit 前の自己チェック（主体が in-context で行う）」節と**同型**（durable 成果物へ書き込む前に、
書く主体が in-context で自問する、という共通パターンの capture 版）。それらの中身（符牒展開・secret/PII
検出）は再記述しない——本節が問うのは別軸（粒度・scope）。

問うべきこと:
- **1件1ルールになっているか**（複数の主張が同居していないか）。
- **固有の事実と一般形が混ざっていないか**（混ざっているなら書き込む前に分割することになっている）。
- **他プロジェクトでも成立する内容なら、`scope` はそれでよいか**（`scope: local` のまま埋もれさせないことになっている）。

- **適用範囲**: [[capture-learning]] が書き込む先（生層エントリ・蒸留層）すべて。実行主体は capture-learning
  を実行している本人である（in-context・専用 subagent へは委譲しない＝「主体が loop を持つ」原則と同型）。
- **本節はこの一次防御の正本**として扱われている（[[capture-learning]] は本節を名前参照するだけで内容を再記述しない）。
- **昇格時点の確認とは別軸**: ここで見落とした粒度混在・scope の誤りへの最後の砦は、ストアへの昇格時点
  （明示実行の `promote-knowledge`（別スキル））側の責務であり、本節はそれを代替しない。

## 書き方不変: travel 面の自己完結（番号を load-bearing にしない）
知見の実体（判断・なぜ・適用）は**外部参照を開かずに成立**する＝自己完結という決まりになっている。**番号（issue/PR 番号）は load-bearing にしない**決まりになっている。
- **判定基準**: home repo の外で読まれるか。**番号**についてはさらに**load-bearing か**（読者がそれを辿ることを意図した参照か）で判定する（repo 名・org identity には load-bearing の限定は掛からない。下記）。
  - **travel 面**（配布 payload 全体＋グローバル知識ストア側のエントリ）: **load-bearing な番号**・repo 名・org identity を載せない決まりになっている。実体はインラインで書く。
  - **ローカル**（home repo 内だけで読まれる knowledge エントリ・コードコメント）: 番号可（複数 repo が同居するワークスペースでは repo を明示する）。
- これは**新しい原則ではなく既存の同族知見の一般化**であり、統合した1 family として扱われている: 「配布物は非配布 doc を参照しない」（`.docs/` は home repo にしか無い＝travel 面が開けない参照）／「配布物に固有名を焼かない」（固有 repo 名・URL は travel 面で意味を失う）と**同一メタ原則**＝「travel 面は home repo の外部性を前提にした参照を持ち込まない」。

### 参照とリテラルの書き分け（コードスパンで判別する）
issue/PR を**参照**するときは**地の文に書く**決まりになっている（コードスパンで囲まない）。**コードスパンの中身（インラインコード / フェンスされたコードブロック）はリテラル**（実行するコマンド・正規表現・ファイル名・再現用の入力等）であり、参照ではない。番号がコードスパン内に現れる場合は load-bearing でない**例示**（正規表現のテストケース・hex カラーコードの例・禁止パターンの見本・バグ再現用の入力値など、番号自体に意味が無く何番でも成立するもの）であり、上記の不変（番号を load-bearing にしない）には抵触しない。この書き分けにより、監査（`bare-issue-ref` / `travel-issue-ref`）はヒューリスティックではなく構文（コードスパンの内か外か）で参照と例示を機械的に区別することになっている。将来コードスパン内に実参照を書くと監査が見逃す（偽陰性）ため、この規約を守る必要がある。

### home repo 固有パスと配布 payload パスの区別（取っ手を剥がしすぎない）
グローバル知識ストアはハーネスの sync lib 経由でしか消費側へ配られない（ハーネス無しでストアを読む経路が無い）＝「ハーネス導入前提」と割り切ってよい。配布物の中のファイルを根拠に挙げるときは、導入先のパス（`.claude/skills/<name>/SKILL.md` 等。プラグイン形では導入先に存在しない）ではなく**論理パス**（`yosage-dev-harness:<harness/ からの相対パス>`。例: `yosage-dev-harness:lib/gh-review.sh`）で書く決まりになっている。論理パスは**全消費者に必ず存在し travel 面でも grep で再解決できる取っ手**であり、home repo の外部性を前提にした参照ではない。**剥がさない**決まりになっている（`path` 根拠ハンドルとして残してよい）。構造監査が使用中の版のプラグインの中で解決して実在を確かめる（`yosage-dev-harness:` の直後に `/` を含むことが目印。`yosage-dev-harness:implementer` のようなエージェント名の名前空間つき参照とはこの点で区別される）。導入先のパスで書かれた既存の知見は監査が `legacy-payload-path` で報告し、変換スクリプト（`yosage-dev-harness-knowledge-convert-paths`）で論理パスへ書き換えられる。
剥がすべきは**home repo 固有の参照**（issue/PR 番号・home の repo 名・org identity・非配布パス `.docs/` 等）に限られる。混同して配布物のパス参照まで一律に剥がすことはしない。

### 取っ手は必須にしない（昇格ゲートは「剥がすな」に留める）
取っ手を持てない純粋な規範エントリ（コードにも外部出典にも接地対象を持たない判断基準）は必ず存在する。取っ手を必須化すると、(a) それらが昇格できなくなるか、(b) ゲートを通すために存在しないパスが取っ手として捏造される。**捏造された取っ手は検証不能より悪い**（実在しない根拠に「検証済み」の外形が付き、偽の信頼を生む）。持てるなら付ける（推奨）が、**持てないことを理由に昇格を block することはしない**。

- 適用: [[capture-learning]] / `promote-knowledge`（別スキル）は本不変を**名前参照のみ**とする（skill 本体に再記述しない＝restate drift 回避）。
