# コミット / PR タイトル規約（不変条件）

## Conventional Commits（履歴の正本）
squash しない運用なので、**個々のコミットが履歴に残る＝コミットメッセージが正本**として扱われている。
- 形式 `<type>(<scope>): <要約>`（例 `feat(api): ユーザー登録APIを追加`）。
- type 語彙: `feat` `fix` `refactor` `chore` `docs` `test` `perf`（出どころ: Conventional Commits ＋ Angular 規約。正本ラベルは `github/labels.json`）。
- semver: `feat`=minor / `fix`=patch / `!` または `BREAKING CHANGE:`=major（0.x は破壊的も minor）。
- **1コミット=1意味**を意識して積む決まりになっている。

## PR タイトル
- 同じく `<type>: <要約>`。squash しないので**履歴には残らない**＝一覧/通知での人間向け見出しとして扱われている。

## Co-Authored-By 署名トレーラ
コミット末尾に AI 実行モデルの署名（`Co-Authored-By: <実行モデルの署名>`）を付けるかどうかは、**コミット先リポジトリの所有**で判断することになっている。squash しない運用では署名入りのコミットは**後から消せない**ため、判断はコミットの瞬間にしか行えない。

- **自社所有のリポジトリ** → 付けることになっている（既定）。
- **自社所有でないリポジトリ** → [project-profile](project-profile.md) が定める**導入先固有の座標**（利用者所有の profile）に、AI 利用を相手方へ**開示済みである旨の宣言があれば付ける**。**宣言が無ければ付けない。**
  - 「開示済みかどうか分からない」も**未宣言として扱われる**（曖昧なまま付ける方へは倒さない決まりになっている）。
  - **判断の根拠は誰が持つか**: 開示の有無は案件ごとに異なる事実であり、判断そのものは上記の profile 記述に従うことになっている（本ルールが個々の案件の開示有無を決めるのではなく、参照する）。
- **なぜ未宣言を「付けない」側へ倒すか**: 付け忘れの損失（AI 利用の痕跡が残らないだけ）と、未宣言のまま付ける損失（開示していない相手方の成果物へ一方的に記録が残り、しかも表面化しない）は非対称であり、安全側が定まっている。
- 開示の有無という**案件ごとに異なる事実**は本ルール（harness 由来の横断ルール）には書かない決まりになっている。書けば次の配布更新で消えるうえ、他案件で誤った前提になる。案件固有の事実は [project-profile](project-profile.md) の切り分けに従い、利用者所有の profile 側に置くことになっている。

> 末尾の `Closes #<issue>`・マージ戦略（マージコミット）・ベースブランチ・自動マージ禁止は [pr-loop](pr-loop.md) が正本として扱われている。
