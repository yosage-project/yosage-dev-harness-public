# PR 標準ループ（不変条件）

すべての変更は PR を介し、**人間マージで閉じる**決まりになっている。**自動マージはしない**（マージは人間のチェックポイントとして扱われている）。

## ループ
`draft → 一次レビュー → 指摘対応 → gh pr ready → 人間マージ`

1. **draft PR** で出すことになっている（`gh pr create --draft`）。draft＝「一次レビュー前」の状態シグナル。
2. **一次レビュー**: `yosage-dev-harness:code-reviewer` サブエージェントに PR/差分を渡すことになっている（正しさ・整合・規約・セキュリティ）。並列配下なら管理者が、単体ならオーケストレーター自身が dispatch することになっている。**自己判断では素通ししない**決まりになっている。
3. **指摘対応**: レビュー findings は **dispatch 元（メイン/オーケストレーター）に戻る**（一次レビューを dispatch した主体が受信点。並列配下なら管理者、単体ならオーケストレーター自身）。受信したら、指摘に付された性質ラベル（客観的欠陥 / 価値トレードオフ。`yosage-dev-harness:code-reviewer`・`yosage-dev-harness:consistency-reviewer`・`yosage-dev-harness:best-practice-reviewer` が共通で出す）でルーティングすることになっている:
   - **客観的欠陥 / 🔴 Must** → `yosage-dev-harness:implementer` へ差し戻して修正させることになっている（標準に倒すだけなので大半は裁定不要。メインは指摘を再分類する権限を保持する＝ラベルは材料であって裁定ではない）。
   - **価値トレードオフ・スコープ判断（Follow-up/Nit の判別を含む）** → 既定は**メイン**が裁定することになっている。裁定手順は [[grounded-design]] Step3 の裁定分岐（客観的欠陥→標準に倒す／価値トレードオフ→recall に直接裁定する前例があれば適用、無ければ人間へ）を**名前参照**して適用することになっている（新しい裁定基準は作らない）。
   - **例外（純局所トレードオフ）**: recall が直接裁定を持つか、という [[grounded-design]] Step3 の判定テストをそのまま満たす純局所トレードオフに限り、`yosage-dev-harness:implementer` が局所裁定してよいことになっている（判定・可視化・override 権の詳細は `yosage-dev-harness:implementer` 手順5「レビュー対応」）。

   ラベルの種別に関わらず、対応そのものに次の2点が課されている（ラベル分岐の枝ではない）:
   - **修正した側（`yosage-dev-harness:implementer`）は、対応した指摘と対になる箇所（同じ性質を持つ残り・変更/削除の反対側）を、識別子の一致に頼らず再走査する**決まりになっている（消したものの名前は、それを指す記述に出てこないことがある。「どちらも」「両方」のような一般語で対象を指す記述に注意する）。
   - **3ラウンド目以降は、受信点がそのラウンドで出た内容を添えて継続可否を人へ上げる**ことになっている。新しい欠陥が出ないラウンドが1回あれば、そこで閉じる（ここでの「ラウンド」は同一 yosage-dev-harness:implementer セッション内でのレビュー往復回数であり、[[agent-watchdog]] が無進捗時に数える再投入カウンタとは別物・別の閾値。判定を進捗の有無に置き、回数そのものでは打ち切らないという考え方は同型）。

   PR コメント上で対応・resolve することになっている（記録を GitHub に資産化）。スコープ外は issue 化する。修正は同じエージェントを `SendMessage` で継続することになっている（文脈保持）。

   **対応が完了したら、PR 本文の該当セクション（概要・検証結果・実装状況・受け入れ条件のチェック状態等）も現在の HEAD と一致する内容に更新する**決まりになっている（これもラベル分岐に関わらず課されている。上の2点と並ぶ独立の要求だが、`gh pr edit` という別操作を伴うため別立てで扱う）。更新は**部分更新**（差分に関わる記述だけを直す）でよく、**本文全体の書き直しは求めない**——レビュー往復のたびに本文全体を洗い直すコストを避けるため。更新漏れの箇所が残るリスクは、往復回数が増えても本文更新そのものが摩擦にならないことと引き換えに許容されている。
   - **`gh-review.sh`（コメント返信・resolve）との役割分担**: コメントへの返信・スレッドの resolve は「その指摘への対応が終わったこと」の記録であり、**PR 本文の更新を代替しない**決まりになっている——別の記録層として扱われている（返信・resolve は `gh-review.sh` 経由、本文の更新は `gh pr edit` 等の別操作で行うことになっている）。コメント返信・resolve が済んでいても本文が修正前の記述のまま残っていれば、**まだ「対応完了」ではない**（PR 本文だけを読む相手——一覧・通知等——には、コメント欄を辿らない限り古い状態がそのまま伝わる）。
4. **`gh pr ready`** で draft 解除する（＝人間レビュー依頼の合図）→ PR URL を報告することになっている（一次レビュー済みの旨）。
5. **人間マージ**。マージは人間が自分の手で行う決まりになっている（許可プロンプトでの承認では代替しない。ハーネスの Bash から PR マージ操作を実行することはできない＝guard がハードブロックする。例外なし）。

## レビュー投稿形式（PR へのレビューの残し方）
一次レビュー（`yosage-dev-harness:code-reviewer` / `yosage-dev-harness:consistency-reviewer` / `yosage-dev-harness:best-practice-reviewer`）の指摘は、
**1回の review 送信**で残すことになっている。投稿は `yosage-dev-harness-gh-review`
経由で行うことになっており、`gh api` は直接叩かない（許可を意味単位のラッパー呼び出しへ寄せることで、`gh api` の
破壊的サブ経路まで一緒に許可してしまう事故を避けている）。渡す入力は `body`＝サマリ /
`comments[]`＝各指摘を `path`+`line` に / `event`＝要修正 `REQUEST_CHANGES`・所感のみ `COMMENT`。
指摘の置き場は**その指摘が特定の行にひもづくか**で決めることになっている（「インライン一択」でも「サマリ一括」でもない）:
- **行にひもづく指摘 → インライン**（該当行にスレッド）。severity（🔴/🟡/🟢）＋欠陥/トレードオフ
  ラベルを各コメントに付すことになっている。実装者が行単位で対応・resolve できる（step3 と噛む）。
  **行にひもづけられる指摘をサマリ本文に丸めない**（＝避けたい失敗）。
- **行にひもづかない指摘 → サマリ本文**。PR 本文と実装の齟齬・変更全体/方針・変更外ファイル・
  ファイルまるごと欠如・follow-up（issue 化推奨）など。マージ可否の所感・良い点・合否1行もここに置くことになっている。
- **全指摘が行にひもづかない場合は、結果としてサマリのみで正しい**（例: PR 本文と実装が
  食い違うだけ）。無理に行へ貼ることはしない。
- 技術制約: インラインは diff に含まれる行にしか置けない（範囲外は API が弾く）。
- `APPROVE` はしない決まりになっている（マージは人間のチェックポイント）。
- PR 作成者＝レビュー投稿者のとき（solo/`--assignee @me` 運用）は GitHub 制約により `REQUEST_CHANGES` が使えず `COMMENT` になる（`gh-review.sh` が自動フォールバックする）。
- **既存スレッドへの返信**（内容の訂正など）も同じラッパーの `--reply-to <review-comment-id>` 経由で行うことになっている（`gh api` を直接叩かない不変を返信でも維持する）。返信先の id は読み取り API（`gh api repos/<owner>/<repo>/pulls/<pr>/comments --jq '.[] | {id, path, line}'`）で取得することになっている。返信モードの入力 JSON は `body` のみを見る（`comments` は無視・`event` は返信に意味を持たないため渡すとエラーで終了する＝黙っては無視しない）。**返信は冪等ではない**（同じ返信を2回投稿すると重複コメントが2件付く。呼び出し側が二重送信しないよう注意する必要がある）。
- **スレッドの resolve**（手順3「PR コメント上で対応・resolve」の実行手段）も同じラッパーの `--resolve <review-comment-id>` 経由で行うことになっている（`gh api graphql` を直接叩かない）。id は `--reply-to` と同じ REST の review comment id（取得手段も同じ）。内部では GraphQL の `resolveReviewThread` mutation を呼ぶが、REST の id を直接渡せないため、先に `reviewThreads` query でスレッドの node id を引く中間ステップを踏むことになっている（呼び出しは2回・返信の1回POSTとは別経路）。resolve モードは JSON 入力（stdin/`--file`）を使わない。**resolve は冪等**（既に resolve 済みのスレッドへ再度呼んでも `isResolved: true` のまま成功する。返信の非冪等性とは対照的）。unresolve（resolve の取り消し）は提供されていない。存在しない id・review comment ではない id・権限不足の場合は非ゼロ終了する（成功したようには見えない）。

## レーン別の一次レビュー要否
> レーン定義（Direct / Tracked single / Design-first single / Epic）の正本は [[change-lanes]]（本節は各レーンの
> 一次レビュー要否という帰結のみを持つ・定義は再記述しない）。
- **Tracked single / Design-first / Epic** → `yosage-dev-harness:code-reviewer` 必須。
- **Direct（自明な小修正）** → 自己レビューで代替可（ただし `draft → ready → 人間マージ` は踏む決まりになっている）。迷ったら Tracked single に上げることになっている。

## ベースブランチ / クローズ / マージ
- **ベース＝導入先の既定ブランチ**（ブランチ名を決め打ちしない）。単発（Direct・Tracked single）・Epic PR の向け先と、
  作業ブランチの起点はこれに従う。解決の順は **投入時に明示されたもの → 導入先の profile
  （`.claude/rules/<名前>/profile.md`）の宣言 → GitHub の既定ブランチ（`origin/HEAD`）→ どれでも決まらなければ止めて人に聞く**。
  実行は `yosage-dev-harness-base-branch [--declared <明示か profile の宣言>] <リポジトリのルート>`
  （宣言が無ければ `--declared` を省く）。終了コード 1（決まらない）は止めて人に聞き、3（宣言したブランチが origin に無い）は
  宣言の誤りとして止める。実行ファイルは profile の文章を解析しない（宣言はモデルが読んで渡す）。宣言の書式は
  [[project-profile]]。
- **Sub-issue PR の取り込み先の既定は Epic ブランチ**（`epic/<name>`。ベースは上の「ベース」で解決した既定ブランチから作る）。
  Epic の完了時に、Epic の PR で既定ブランチへ取り込む。**既定ブランチへ直接入れる例外**は、`epic-create-docs` で Sub-issue に
  分割するときに**ハーネスが Sub-issue ごとに判断**し、計画と Sub-issue の本文に「取り込み先: <どちらか>（理由）」として書く。
  判断の材料は「独立に取り込めるか」と「先に出したい・Epic の外で先に必要とされている」事情（独立に取り込めて、かつ先に出す事情が
  あるときだけ例外）。人は起票前の計画のレビューで見る。`epic-implement` は書かれた取り込み先に従う。**実装の途中で変えたくなったら、
  ハーネスが変更を提案し、理由とともに Sub-issue に記録してから従う。黙って変えない**。
- **導入先の既定ブランチと実際の取り込み先が食い違う導入先**は、[[project-profile]] の導入先座標に宣言を書いて上書きする
  （上の解決の順の2番目）。
- **クローズ**: Sub-issue は自動クローズに頼らない。PR 本文の `Closes #` は**既定ブランチ向けの PR でしか解釈されない**ため、
  Epic ブランチ向け（直列に積んだ先行ブランチ向けを含む）の Sub-issue の PR では発火しない。Epic ブランチ向けの PR の本文には
  `Closes #` ではなく「Part of #<Epic>」と Sub-issue への参照を書く。Sub-issue は、**Epic ブランチへのマージを確かめた時点で
  統制側が、マージされた PR へのリンクを添えて明示的に閉じる**（`epic-implement` 手順7）。既定ブランチへ直接入れる例外は従来どおり
  PR 本文の `Closes #` で閉じる。
- **コミット末尾の `Closes #<Sub-issue>` は残す**（Epic ブランチの履歴から取り込みを確かめるために使う。単発・例外では自動クローズも兼ねる）。
- **Epic ブランチを作る条件**は [[epic-create-docs]] が正本（取り込み先が Epic ブランチの Sub-issue があれば作る、等。ここでは再記述しない）。
- **Epic の PR は draft で作る**（既定ブランチ向け。Epic の間の取り込み漏れの受け皿）。単一リポジトリは `epic-create-issues` が起票のとき、
  ワークスペースは `epic-implement` が最初の Sub-issue を Epic ブランチへ取り込んだ時点で作る。完了時はこの PR を ready にして人がマージする。
- **Epic の完了時に必ず満たす状態**（満たさなければ案内して止まる）の正本は `epic-implement` 手順8（[[epic-implement]]）。ここでは再記述しない。
- マージは**マージコミット**とする決まりになっている（squash しない・rebase しない）。
- PR 作成時は `--assignee @me`（作成者＝自分）を付けることになっている。

## マージ後の掃除（レーン共通）
掃除の要否は**レーンに依存しない**——Direct / Tracked single / Design-first single / Epic の
どれを通っても、マージすればローカルブランチが残る。**要求はこの節に一本化**することになっており、他は本節への
名前参照に置き換えることになっている（同じ要求を複数箇所へ再記述しない）。

- **トリガ**: 人間マージを確認できた時点（上記ステップ5の直後）。次の作業に入る前に行うことになっている。
- **最初に手元の base を進める**: 遅れた base に対し `git branch -d` はマージ済みも未マージと判定する。掃除の前に
  `yosage-dev-harness-update-base [--declared <ベースと同じ宣言>] <リポジトリのルート>` を実行し、非0なら理由を人に知らせる
  （掃除は続けてよい。`-d` で消せず残ったブランチも合わせて知らせる）。
- **削除は失敗する側に倒すコマンドで行う**決まりになっている（人手の確認・「push 済みか」の判定には頼らない）:
  ブランチは `git branch -d`（`-D` は使わない）、worktree は `git worktree remove`
  （`--force` を付けない）を使う。未マージのブランチ・未コミットの変更が残る worktree では
  これらのコマンド自体が失敗するので、**その場合は削除せずそのまま残し、要否の判断を
  人に委ねる**ことになっている（force で押し切って変更を失わせることはしない）。
- **削除後にリモートブランチから再取得できるとは限らない**（リポジトリ設定に依存する。例: GitHub の
  `delete_branch_on_merge` が有効だとリモート側も消える）。この節は導入先の設定を前提にせず、
  「リモートに残るから安全」とは言わない。安全性の根拠は「失敗する側に倒すコマンド」だけに置く。
- **一括削除ではなく名指しで消す**: ブランチの掃除は、**その作業が作ったブランチを名指しで
  消す**決まりになっている。「残す方（base ブランチ等）を列挙して、それ以外を一括削除する」形は取らない
  （例: `git branch --merged <base> | grep -v '<base ブランチ名など>' | xargs git branch -d`）。
  この形は、除外リストに保護すべきブランチ（リリース専用ブランチ等、既定ブランチとは別に
  運用しているものを含む）を1つでも書き漏らすと、それを巻き込んで削除してしまう。実際に、この形の
  一括削除でリリース専用ブランチが巻き込まれかけた事例がある。
  - **guard による機械的ブロックは採らない**: `xargs` 等を経由する一括削除では、削除対象の
    ブランチ名がコマンド文字列に現れない（パイプの上流が実行時に決める）。guard は静的な
    テキスト解析なので原理的に検知できない。「guard で止めればよい」の再提案で同じ検討を
    やり直さないよう、理由をここに固定する。
  - **保護すべきブランチ集合は単一ホームが持つ**: base ブランチ・`main`・`master`・epic
    ブランチ等の保護対象は `lib/branch-protection.sh` が1箇所で列挙することになっており、`lib/epic-cleanup.sh`
    はそこを参照することになっている（除外リストを個別に持たない＝二重管理にしない。取りこぼしは1箇所の
    修正で直る）。
- **Epic 固有の追加要件**: Epic は複数の Sub-issue が並行して走り、他タスク・他 Epic の現役 worktree と
  同居しうる。「merge 済みか」「worktree 置き場の配下か」だけでは対象を絞れない（無関係な稼働中
  worktree を巻き込みうる）。Epic 集合に限定する専用ロジックとその実行手順は [[epic-implement]] 手順9が
  持つ（本節は再記述しない）。単発（Direct・Tracked single・Design-first single）は、自分が作った
  1本のブランチ・worktree を消すだけでよい。
