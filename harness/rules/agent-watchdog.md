# agent watchdog（不変条件）

ディスパッチした agent（yosage-dev-harness:implementer / yosage-dev-harness:researcher / yosage-dev-harness:explorer / reviewer / yosage-dev-harness:architect / yosage-dev-harness:doc-writer 等）が
**スタックして数十分無成果**になることを防ぐ運用になっている。原則は**長くても動いていれば殺されない。止まっていたら切られる。**というものである。

**適用対象は agent dispatch に限らない**: オーケストレーター自身が `Bash` の `run_in_background` 等で
直接起動する長時間プロセスにも同じ有界待ち原則が適用される。実行主体が別 agent か自分自身の
バックグラウンドプロセスかは、受け身に待つと停止検知が効かなくなるという構造上の問題に関係しない
——完了通知を待つだけの受け身姿勢は、相手が agent であれプロセスであれ同じ不可視性を生む。

## 管理者側（ディスパッチした主体 / バックグラウンドプロセスを起動した主体）
1. **受け身の無限 await はしない決まりになっている**: dispatch した agent の完了待ちに限らず、**自分で起動した
   バックグラウンドプロセスの完了待ちも同様**に、必ず**有界待ち**で回すことになっている（`TaskOutput(block:true,
   timeout=心拍)` の繰り返し、`Monitor` で進捗条件＋上限、または Bash の場合は同種の有界ポーリング
   ループ）。ハングは完了通知が来ない＝受け身だと不可視（agent か自プロセスかを問わない）。
   - **自然終了が保証されないプロセス種別には特に注意が要る**: 外部ツール実行（GUI 操作・シミュレータ
     操作を伴うもの等、例: モバイル UI 自動操作 CLI）は、ツール側・環境側の問題で処理が一切進まない
     まま停止することがあり、かつ自発的にタイムアウトしてプロセスを終了させるとは限らない。この種の
     プロセスを `run_in_background` で起動する場合は、単純な受け身待ち（「完了通知が来るまで待つ」）
     ではなく、`Monitor` 等の**有界待ち**で進捗（ログ出力・状態変化）を能動的に確認しながら回すことになっている。
2. **心拍ごとに“ネット進捗”を見る運用になっている**: 種別ごとの進捗シグナル（yosage-dev-harness:implementer/yosage-dev-harness:test-writer＝ブランチ HEAD が**新しい所へ**前進 / yosage-dev-harness:researcher・yosage-dev-harness:explorer＝出力の実質増 / reviewer＝完了 / yosage-dev-harness:architect・yosage-dev-harness:doc-writer＝前進 / **生プロセス**（`run_in_background` 等・会話不可能）＝**標準出力/ログファイルへの新規出力（増分）**）。
   **「動いている」≠「進んでいる」**: 同じ所を行き来して収束しない・同じ出力の繰り返しは**実質ストール**として扱われる。
3. **kill はストール一本（時間では kill しない）決まりになっている**:
   - ネット進捗あり → **続行（時間制限なし）**。長いだけでは罰されない。
   - ネット進捗なしが続く（**会話可能な agent**） → **nudge** → 具体的進捗が返れば**リセットして続行** / 無反応・空回りなら **`TaskStop`**（worktree/ブランチは残す＝途中成果を捨てない）→ 原因記録 → **1回だけ再投入** → ダメなら**人間へエスカレーション**する運用になっている。
   - ネット進捗なしが続く（**生プロセス・会話不可能**） → nudge を試みず**直接 kill** → 原因記録 → **project-profile に復旧手順の宣言があればそれに従って実行**（[[project-profile]]） → **人間へ報告**する運用になっている（再投入するかは人間判断に委ねる。item6 の分類は会話可能な agent 向けの語彙であり生プロセスには拡張しない）。
4. **長いが動作中 → 切らず通知（ソフト上限）**: kill せず agent に「**なぜ遅いか**」を報告させ、人へ「続ける？切る？」を出す運用になっている（自動では切らない）。
5. **nudge の2用途（会話可能な agent 限定）**: 生プロセスは応答できないため本項は適用されない（無応答時の扱いは item3 の生プロセス向け分岐を参照）。
   - **ストール確認**（無進捗時）: 「詰まってる？原因と要るものは？ 粘らず停止報告でよい」という問いかけになる。
   - **遅延理由**（長いが進捗時）: 「現状＋なぜ遅いか」を分類で返させる → **外部待ち**（CI/ネット/認証）＝続行寄り or 人が解く / **量が多い**＝続行寄り / **試行錯誤で無収束**＝切る寄り / **ブロック**（依存・判断待ち）＝停止報告、という振り分けになっている。
6. **再投入は原因で打ち手を変える（自動リトライは1回。会話可能な agent 向け）運用になっている**: 文脈不足/曖昧 → 足して同ユニット再ディスパッチ / スコープ過大 → 分割 or 後続ウェーブへ延期 / 共有リソース競合（DB/ポート/compose stack）→ メインが直列で引き取り / 外部依存待ち → 人へ依頼、という打ち手が対応づけられている。

## worker 側（ディスパッチされた agent）
- **黙って長引かせない＝自己心拍**: 長い処理に入る時は自分から一言（「大きいテスト実行中」「N ファイル横断中」）を伝える決まりになっている。
- **nudge されたら**: 進捗 ＋ 遅延理由（上の分類）を1行で返すことになっている。
- **詰まったら停止報告**: 無限リトライ・空回りはしない。進めない時は早く止め、理由を添えて報告する（黙って粘らない）決まりになっている。
