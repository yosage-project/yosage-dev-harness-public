# 設計ルーティング / 討議着火ゲート（不変条件）

**変更依頼を受けたら、実装 dispatch より前**に設計討議が必要かを判定することになっている。主語は「変更の受け付け時点〜実装 dispatch の間」に厳密に限定される。実装 dispatch 以降のルーティングは [[implement-routing]] が担う（上流→下流の別フェーズ）。

> **視覚デザイン（見た目・配色・タイポグラフィ・レイアウトを起こす）は別レーンとして扱われている**。本 rule が扱う「design」はソフトウェア設計（仕組みをどう作るか）に限られる。視覚デザインの判定・入口は [[visual-design-routing]] を参照。

## レーンを分類して討議の要否を判定（着手前・必須）

変更依頼のレーン定義（Direct / Tracked single / Design-first single / Epic）の正本は [[change-lanes]]。
ここでは**討議着火の actionable 最小基準だけ**をインラインで持つことになっている（下表の3分類は [[change-lanes]] の定義そのものではなく、討議着火軸の別プロジェクション）。

| 分類 | actionable 判定基準 | 討議の着火 |
|---|---|---|
| **Direct** | 自明な小修正。設計判断なし・後戻り低・同セッションで完結 | **討議しない（明示除外）** |
| **Design-first（軽め）** | 複数案があるが局所的・後戻りコストが低い | **harness が自己着火**（直接 [[deliberate-design]] へ入る。入口が軽い＝即 exit 可） |
| **Epic / 大きめ（重め）** | 後戻りが高い or Epic 級（アーキ横断 / 複数 Sub-issue） | **harness が検知して提案・確認** → 人間が承認して着火 |

- **迷ったら討議寄せ（ただし Direct は明示除外）**: 判断がつかない場合は Design-first 以上として扱われる。Direct は「設計判断なし」が明確な場合のみ適用される。
- **人間の手動発火はいつでも可**: どのレーンでも人間が `/yosage-dev-harness:deliberate-design` 等で直接着火できる。

## 着火モデル（実装）

### Direct — 討議しない
Direct と判定した変更はそのまま実装フローへ進む（[[implement-routing]] へ）。討議のオーバーヘッドは掛からない。

### 着火可否の原則（インライン）
**着火可否は遷移の重さ（コスト/戻しにくさ）で切る**: 思考フェーズの軽い入口（設計討議への入場＝読む・考える・喋るだけ）は harness 自己着火可。重い着火（実装 dispatch・Epic 一括・Epic 級討議への入場）は人間トリガ＋コマンド提案（実装 dispatch のみ、profile で人が委譲を宣言した範囲ではメイン（オーケストレーター）が着火してよい。条件は [[implement-routing]]）。

### Design-first（軽め）— harness 自己着火
軽い Design-first は harness が自己着火することになっている（人間の承認は待たない）。
設計討議への入場は「読む・考える・喋るだけ」で安く即戻せるため、自己着火が許容される。
- 入口の軽さを保つ: 討議に入っても人間は即 exit / decline できる。
- [[deliberate-design]] を呼び出して討議ループを開始することになっている。

### Epic / 大きめ（重め）— harness が提案・確認
重い設計については harness は**自己着火しない**決まりになっている。代わりに次の手順を踏む:
1. 「設計討議が有益そうな変更を検知した」旨を人間に提示することになっている。
2. 討議コマンド（`/yosage-dev-harness:deliberate-design` 等）を**正確に提示**し、承認を求めることになっている。
3. 人間が承認した場合のみ [[deliberate-design]] へ入ることになっている。

自己着火しない理由: Epic 級の討議着火は重い（アーキ横断の議論・複数人が関わりうる）。誤着火のコストが高く、人間ゲートが安全側デフォルト。

## implement-routing との接続

`design-routing`（設計要否の判定）と [[implement-routing]]（実装 dispatch のルーティング）は**時系列で隣接する別フェーズ**:
- `design-routing` の出力（合意した設計 / design-doc issue）が `implement-routing` の入力になる。
- 討議の出口→実装 dispatch の着火は従来どおり **`implement-routing` の人間ゲート**（profile で委譲を宣言した範囲の例外も同ルールが持つ）。
- 設計フェーズを省略して直接実装 dispatch に進む場合も `implement-routing` を経由することになっている。

## 過剰着火の歯止め

- Direct を明示除外することで「何でも討議化＝摩擦」を防ぐ。
- 自己着火しても入口が軽く（討議を始めるだけ）人間が即 exit できる。
- 討議規律の詳細（比較盤・収束基準・ラウンド上限）は [[deliberate-design]] が担う（本 rule に再記述しない）。
