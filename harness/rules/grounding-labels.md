# 接地ラベル（不変条件）

設計・ドキュメントでは**主張の出どころを明示**し、無自覚な補完を表面化することになっている。各主張に根拠ラベルを付ける決まりになっている:

- `✓内部 path:line` — 既存コード/doc に実在（**要 path:line**）。
- `✓外部 出典` — 外部ベストプラクティス/spec（**要 URL/出典**）。
- `✓実測 <観測構成>` — 動かして確認した実行時の主張（**要 観測構成**: 何をどう動かして何を観測したか。「動かして確かめた」だけでは不足）。コードを読んでも外部出典を当たっても決着しない、このシステム自身の実行時の振る舞いに対する接地ハンドル。
- `§仕様` — 与えられた要件/spec に明記。
- `≈慣例` — 一般的な慣例（出典は弱いが広く採用）。
- `+補完(要確認)` — 根拠が無く補完した推測（**要確認**）。動かさないと決着しない実行時の主張が未検証のまま残る場合もここに含め、**確認手段が実測であること**と**どう動かせば決着するか**を併記することになっている。
- `⚠内部≠外部(要判断)` — 内部の前例と外部標準が食い違う（**要判断**）。

- `+補完` と前提は **「## 補完・前提（要確認）」** セクションに集約し、ユーザー確認に回す決まりになっている（後出しの 1-Q-1-A 訂正を減らす）。未検証の実行時の主張もここに残す（専用ラベルは新設しない）。節自体が量が有界（1 doc の1節）で人間が一度に前さばきできるため、記号を増やさなくても「人に聞いて決着する」補完と「動かして決着する」補完の違いは、節内で確認手段を1行書くことで表現できる。節に未検証の実行時の主張が溜まり前さばきしきれなくなったと判明した時点で、専用ラベルの新設を再検討することになっている。
