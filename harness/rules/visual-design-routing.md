# visual-design-routing（不変条件）

## 「design」の二義性（正本）

同じ語「デザイン/design」が2つの異なる作業を指しうる。混同すると、討議儀式を持ち込むべきでない場面に持ち込んだり、
逆に本来討議すべき仕組みの判断を視覚レーンで素通りさせたりすることになる。

- **ソフトウェア設計**（何をどういう仕組みで作るか） — アーキテクチャ判断・ビルド基盤選定・コンポーネント設計・データモデル設計。
  対象スキルは `deliberate-design` / `design-doc` / `grounded-design` / `document-architecture`。討議の入口判定は [[design-routing]]（本 rule はそちらへフォークするだけで、着火判定軸自体は変えない）。
- **視覚デザイン**（どう見えるか） — 色・書体・レイアウト・UI の見た目を起こす作業。対象スキルは [[visual-design]]。本 rule が担う。

## いつ視覚レーンに入るか（intent 判定）

作業が**見た目・配色・タイポグラフィ・レイアウトを起こす／作り直す**ことを目的にしているかで判定することになっている。
「UI のビジュアルを起こしたい」「配色を決めたい」「テンプレっぽくない見た目にしたい」のような依頼は視覚レーンに入る。
「どういう仕組みで作るか」「アーキをどうするか」を決める依頼はソフトウェア設計レーン（上記）に入る。

判定は `paths:` によるファイルパス限定ではなく、**依頼の intent** で行うことになっている（UI ファイルを触るからといって自動的に視覚レーンになるわけではない。例えばコンポーネントの状態管理ロジックを直す作業は見た目を起こしていないためソフトウェア設計レーンになる）。

## 境界のグレーゾーン（切り分け例）

design system はソフトウェア設計と視覚デザインの両方にまたがりうる。判断に迷ったら以下を目安にすることになっている:

- **ビルド基盤・フレームワークの選択・コンポーネントの構造設計**（どう組むか） → ソフトウェア設計側。
- **色・書体・レイアウト・spacing・signature（どう見えるか）** → 視覚デザイン側。

同じ作業の中で両方が出てくることもある（例: 新しい UI コンポーネントを追加するとき、構造の判断はソフトウェア設計レーン、その見た目のトークン決めは視覚デザインレーン）。作業は分けて、それぞれのレーンの手順で進めることになっている。

## 視覚レーンは deliberate-design の討議儀式を踏まない

視覚デザインでは `deliberate-design` の多案比較＋二軸レビューは行わない。既定解を避ける強制関数は多案発散ではなく、
[[visual-design]] 内の批評ゲート（トークン系をブリーフと照らし「既定解になっていないか」を批評する工程）が担う。
このためハーネスの討議儀式をその上に重ねると、同じ役割の儀式を二重に踏むことになってしまう。

美的な品質はスコアで客観的に裁定できないため、収束は人間が見て選ぶことになっている（[[visual-design]] の「発散の提示形」を参照）。

## knowledge フック

視覚デザイン作業の着手時・確定後は [[recall-knowledge]] / [[capture-learning]] を通すことになっている（ルール `knowledge` の recall/capture 規律に従う。本 rule はポリシーを再記述しない）。捕捉先は consumer 固有の `ui/` domain とされている。
