# document-profile — 導入先固有の profile.md を起こす／鮮度チェックする（明示実行）

ルール `project-profile`（常時オン）が定める「導入先固有の座標は
`.claude/rules/<名前>/profile.md` に置く」という置き場を、実際に**調査して起こす**手段。
**人間が明示的に起動**し（`/yosage-dev-harness:document-profile` または `/yosage-dev-harness:document-profile refresh`）、
下書きを人間が確認してから書き出す。所有権と、書き出し後の扱いは `project-profile` 正本を
参照（本 skill には再記述しない）。

引数無し＝モード1（新規作成）。`refresh`＝モード2（鮮度チェック）。

## モード1: 新規作成

1. **対象を決める**: 単一 repo で動いているならその repo。複数 repo が同居するワークスペース
   なら、どの repo の profile を作るか利用者に確認する。ここで選ぶのは調査対象の repo であり、
   書き出し先は対象が member repo なら常にワークスペース側になる（手順5で確定する）。
2. **調査**: `yosage-dev-harness:explorer` サブエージェントに委譲し、対象を調べる。少なくとも次を拾う: スタックと
   パッケージマネージャ（バージョンピンを含む）・ビルド/テスト/lint コマンド・CI 設定が実際に
   何を走らせているか・base ブランチ・ブランチ命名の実例・PR/issue テンプレートの有無・運用
   ラベルの実在・**GitHub の既定ブランチ（`origin/HEAD`）と、実際の PR の向け先・既存 profile の base ブランチの宣言との比較**
   （食い違うときだけ、`project-profile` 正本の書式 `` - **base ブランチ: `<名前>`** `` の1行を下書きに入れる。一致していれば書かない）・**実装の着火の委譲の有無（`project-profile` 正本の書式 `` - **実装の着火の委譲: `単発 issue`** `` の1行。既存の宣言を読み取るだけで、無ければ下書きに入れない。委譲するかは人が決めること）**・**検証コマンドのうちどのサブセットが排他資源（`project-profile` 正本の「検証時
   排他資源」項目。固定ポート・特定 UDID/AVD・共有ビルドディレクトリ・keychain 等の単一インスタンス
   資源）に依存するか**（コマンド全体ではなくサブセット単位で尋ねる。unit/lint/build のような高速
   フィードバック層まで不必要に遅延させないため）。
3. **重複除外**: 収集した項目ごとに、次の3つの軸で下書きから外すか判定する。
   - **`.docs/` に正本を持つか**: 持っているなら書かない（`project-profile` 正本が定める境界。
     ここでは再記述しない）。少なくとも `glossary`（ドメイン語彙の正本）・
     `document-architecture`（ディレクトリ構成/アーキテクチャの正本）が持つ内容と突き合わせる。
   - **harness の横断ルールが既に定めているか**: PR ループ・issue 規律・コミット規約など、
     harness の横断ルールが既に定めている事項も profile へ再記述しない（`project-profile`
     正本と同じ理由: 横断ルールが変わると profile が追従できず drift する）。
   - **規約と実態が一致しているか**: 一致しているなら書かない（差分がゼロのため）。書く価値が
     あるのは、実態が規約からズレている場合（規約に無い書き方が実例として残っている、設定
     ファイルの意図が適用されていない、等）と、規約がそもそも触れていない実測値（テストの
     所要時間・並列実行の禁止など）だけ。ズレを書くときは、腐りやすい参照（コミットハッシュ
     等）を根拠として載せない（実態の記述だけで判断が成立する形にする）。

   profile が持つのは**導入先固有の差分だけ**。
4. **下書きを提示**: 収集結果を「座標（repo 名・base ブランチ・PR/issue の慣習・運用ラベル等）」
   「アプリ構成（スタック・パッケージマネージャ・主要な設計パターンと落とし穴）」「検証コマンド
   （ビルド/テスト/lint。CI 準拠）」「アダプテーション（この導入先固有の注意）」のような節立てで
   まとめ、利用者に提示する。節数・粒度は対象に応じて増減してよい。各節について「`.docs/` 側の
   正本と重複していないか」を利用者が確認できる形にする。手順3で規約と一致していたために
   落とした項目も、その理由（差分がゼロだったため）とあわせて提示に含める（調査漏れと誤解
   されないため）。
   **利用者の確認を経ずにファイルを書き出さない。**
5. **書き出し先を決める**: 対象がワークスペースの一員（member repo）である場合は、**ワークスペース
   側の `.claude/rules/<repo 名>/profile.md`** に書く。
   **メンバー repo 自身の `.claude/rules/` には置かない**。ワークスペースかどうか・member かどうかの
   判定は `yosage-dev-harness-config-get workspace` の値（`yosage-dev-harness:librarian` と同一基準）を
   用いる。単一 repo（ワークスペースではない）の場合はその repo 自身の
   `.claude/rules/<名前>/profile.md` に書く。
6. **書き出す**: 利用者の確認・修正を反映した内容を、決めた書き出し先へ書く。
   **`paths:` frontmatter は付けない**（常時オンにする。`CLAUDE.md` と同格で起動時ロードされ全
   subagent に継承される。理由は座標が対象のファイルを開く前の調査・設計・委譲ブリーフ作成の時点で
   必要になるため）。常時オンの代償は全 subagent が毎セッション払うトークンなので、手順3の重複
   除外を怠らない。

## モード2: 鮮度チェック（`refresh` 引数）

1. モード1の手順5と同じ判定で既存 `profile.md` の所在を決め、読む。
2. **再解決できる形で書かれている記述**だけを対象に、実体と突き合わせる: 記載されたコマンドが
   実在するか（`package.json` の scripts 等）・base ブランチ名が実在するか（宣言があれば、GitHub の既定ブランチ・
   実際の PR の向け先と突き合わせ、食い違いが解消していれば宣言が不要になっていないかも見る）・参照している path が
   生きているか。自然文で書かれた注意書き（落とし穴の説明など）の正しさは機械的に判定できない
   ため対象外。
3. **ズレを列挙して提示する。自動では直さない。**
4. 利用者が採否を決めて反映する。反映の書き込みも利用者の指示を経てから行う。

## 知見を残す（knowledge loop）
- **前**: 着手前に [[recall-knowledge]] で対象ドメインの過去の判断・落とし穴を recall する。
- **後**: profile を確立/更新したら、その過程で得た再利用可能な知見（採用した項目・除外した
  重複・見つかったズレのパターン）を [[capture-learning]] で蓄積する。**作業した本人**が回す
  （誰が回すかは ルール `knowledge`）。

## 原則
- **調査してから書く**: 憶測で埋めない。調査は `yosage-dev-harness:explorer` に委譲してよい。
- **確認を経て書く**: 新規作成・鮮度チェックのどちらも、書き出し/反映は利用者の確認を経る。
- **差分だけを持つ**: `.docs/` の正本・harness 横断ルールが既に持つ事項、規約どおりに運用されている
  実態を profile に重複させない（判定軸は手順3）。
- **所有権は `project-profile` 正本を参照**: 書き出し後の扱いは本 skill には再記述しない。
