# orchestrate-parallel — メインセッション＝司令塔

複数作業を worktree エージェントで並列実行するとき、**メインセッションは自分で実装せず、計画・分配・監視・統合・判断に徹する**（司令塔/管理者）。
狙いは2つの失敗を防ぐこと:
- **① ストール放置**: 並列エージェントがエラー/停止しているのに気づかず、数十分待って無成果。
- **② コンフリクト**: 衝突する作業を並列にして、互いのコミットがぶつかる。

## 使う道具（Claude Code）
- 起動: `Agent`（`run_in_background: true`, `isolation: "worktree"`）。バックグラウンド隔離実行、完了時に通知。
- 監視: `TaskOutput`（`block: false` で**非ブロッキング**に状態確認 / `block: true`＋短い `timeout` で上限つき待機）、`TaskStop` で停止。
- 心拍: `Monitor` でブランチの最終コミット時刻やタスク状態を一定間隔監視し、ストールを早期検知。
- 台帳/依存: `TaskCreate`/`TaskUpdate`（`addBlockedBy`）でユニットとウェーブ依存を管理。
- 注意: local agent の `.output`（会話トランスクリプト）は **Read しない**（コンテキスト溢れ）。状態確認は `TaskOutput` を使う。

## 手順

### 1. 計画と分割（コンフリクト回避）
- 各作業ユニットの **対象ファイル/ディレクトリ集合** を洗い出す。
- **衝突グラフ**を作る: 同じファイルに触るユニット同士は衝突 → **並列にしない（直列化）**。
- 論理依存（A の成果を B が使う）も直列。
- **作業単位に `直列実行:` 宣言があれば直列化**（著者が宣言した直列指定を honor。ファイル/リソースが素に見えても＝conflict-driven が見落とす衝突の補完）。
- **ファイルだけでなく共有リソースの衝突も見る**: 同じ DB / ポート / compose スタック / 外部状態（同一 Issue/PR/ブランチ）を奪い合うユニットも衝突扱い → 並列にしない（詳細は「並列の安全性」）。
- **互いに素なファイル集合 ＋ 素なリソース ＋ 依存なし** のユニットだけを 1 ウェーブにまとめる。残りは後続ウェーブへ。
- 同時実行数に上限（監視可能な範囲、例 3〜4）。

### 2. ディスパッチ（ウェーブ単位）
各ユニットを **`yosage-dev-harness:implementer` サブエージェント**で worktree/background 起動する。実装規律（接地・規約遵守・
コミット規約・draft PR・capture-learning・詰まったら停止報告）は **yosage-dev-harness:implementer 定義に内蔵**されているので、
管理者が渡すのは **作業単位 ＋ 担当ファイル範囲** で済む。念のため指示に含める:
- **担当ファイルの範囲を明示**（範囲外を触らない）。
- 完了時に **commit + push**（未 push は worktree 掃除で消える）。
- **詰まったら/不確実なら、回らずに停止して報告**（無限リトライ・空回り禁止）。
- 各タスクの id・対象ファイル・ブランチを記録（必要なら `TaskCreate` で台帳化）。

### 3. 監視（ストール検知 ＝ 最重要）
**エージェント watchdog に従う**（ルール `agent-watchdog` — 常時オンの正本）。並列での実現:
- **受け身で待たない**: `TaskOutput(block:false)` の定期確認 ＋ `Monitor` で「各エージェントブランチの最終コミットからの経過」を心拍監視（＝ネット進捗の確認）。
- **ストール（watchdog 判定）を検知したら**: `TaskStop`（worktree は残す）→ 出力確認 → 1) 文脈を足して**再ディスパッチ** / 2) メインが**引き取り** / 3) 後続ウェーブへ**延期**。

### 4. レビュー → 判断（**PR 上で**。レビューを資産化）
**標準PRループに従う**（ルール `pr-loop` — 常時オンの正本）。以下はその**並列オーケストレーション版の手順**。
ローカルでぐるぐる回さず、**PR 上でレビューする**。指摘・対応・解消が GitHub に残り、レビュー自体が監査可能な資産になる。

1. **draft PR で出す**: 実装エージェントは完了したら **draft PR** を作成（`gh pr create --draft`）。
2. **レビュー依頼（URL を渡すだけ）**: 管理者はレビュー用サブエージェント（`yosage-dev-harness:code-reviewer` / `yosage-dev-harness:consistency-reviewer`）に **PR 番号/URL だけ**渡す。レビュアーは PR/ブランチを直接読み、観点（各レビュアーの定義の観点 ＋プロジェクト固有 `.docs/architecture`・`.claude/rules`・`.claude/yosage-dev-harness-review-criteria.md`。`yosage-dev-harness:code-reviewer` はさらに組織の観点 `.claude/review/criteria.md` を読む）を適用。
3. **PR にコメントを残す**: レビュアーは指摘を PR のレビューコメントとして投稿する（投稿形式は pr-loop の「レビュー投稿形式」に従う＝行にひもづく指摘はインライン・ひもづかない指摘とサマリは本文へ）。合否（要修正 / 問題なし）を管理者へ返す。
4. **管理者が判断**:
   - **要修正** → `SendMessage` で実装エージェントへ差し戻し。実装側は **PR コメントに対応**して push し、**対応済みスレッドを resolve** → 再レビュー。実装側は対応に加え、再発防止の判断基準を **`capture-learning`** で蓄積する（本人の文脈で。レビュアーではなく作業した本人が行う）。
   - **スコープ外 / 現 PR で直さない指摘** → **GitHub issue として起票**して追跡する（落とさない。起票はスキル `issue-create`・ルール `issue-discipline` に従う）。
   - **問題なし** → 次へ。
5. **ループ上限**: 2〜3 往復で収束しなければ人間にエスカレーション。
6. **人間にレビュー依頼**: 指摘が解消したら **`gh pr ready`** ＋ 人間へ報告（PR URL ＋ 一次レビュー済みの旨）。以降の ready→人間マージは正本（`pr-loop.md`）どおり。

> 管理者が運ぶのは **PR URL と決定だけ**。diff・レビュー全文は GitHub と各エージェントにあり、管理者のコンテキストに抱えない。

### 5. 逐次統合（コンフリクト解消）
- 完了したサブブランチは **1本ずつ** 統合（Epic ブランチ等へ）。マージ戦略は ルール `pr-loop`（マージコミット）。
- 統合のたびにテストを回す。次のブランチが衝突したら、**司令塔（メイン）がコンフリクトを解消**する（または敗者を rebase して再実行）。
- 直列統合なのでコンフリクトは必ず予測可能な箇所で表面化し、取りこぼさない。

### 6. 回収と再計画
- 失敗/ストールしたユニットは原因を記録し、範囲を切り直して後続ウェーブで再実行 or メインで対応。
- worktree とローカルブランチの削除は **push/PR 済みのものだけ**（未 push は消さない）。

## 並列の安全性（衝突点と対策）
worktree は **ファイルを隔離**するが、それ以外の共有資源は隔離されない。

- **ファイル**: ✅ worktree で隔離（各エージェント別ディレクトリ）。担当範囲外を触らせない。
- **共有 compose スタック(DB/ポート/コンテナ名)**: ⚠️ worktree では隔離されない。
  - 並列エージェントに **共有スタック依存の作業（マイグレーション / DB を使うテスト / `docker compose up`・`exec` / 同一ポート）を走らせない**。
  - stack 依存の検証は **管理者(メイン)が直列**で行う。
  - どうしても各自で要るなら、エージェントごとに `COMPOSE_PROJECT_NAME=<unique>` ＋ 動的ポートで **使い捨てスタックを分離**（重いので最小限）。
- **テスト実行（並列衝突の筆頭）**: 共有スタック/DB/コンテナへのテストは並列でポート競合・DB 状態の競合・flaky を招く。
  - 既定: 管理者(メイン)が **直列**で回す（worktree エージェントに走らせない＝既存の「テストは main から」）。
  - 並列で回すなら各自に **隔離した使い捨て環境**（`COMPOSE_PROJECT_NAME=<unique>`＋動的ポート＋使い捨て DB、または `scratch.sh`）。
  - 共有資源に触らない **ユニットテスト**は並列で安全。
- **使い捨て実行(`scratch.sh`)**: ✅ `--rm` ＋ 各自の `$PWD` マウントで並列安全。固定 `--name`／固定ポートを使わない。
- **検証時排他資源（project-profile 宣言）**: ⚠️ worktree では隔離されない。DB/ポート/compose スタックと同じ
  奪い合いが、モバイルシミュレータ/エミュレータの具体インスタンス・共有ビルドディレクトリ・keychain 等の
  単一インスタンス資源でも起きる。導入先固有の座標（ルール `project-profile` 正本の
  「検証時排他資源」項目）に宣言されているものは、その検証だけを対象にした PR 単位ゲート（Sub-issue/単発 issue
  の実装レーン——`.claude/skills/epic-implement-subissue/SKILL.md` / `.claude/skills/issue-implement/SKILL.md`
  ——が `gh pr ready` 前にメインが直列で行う）で受ける。
- **外部状態**: 1ユニット = 1ブランチ = 1 PR（同じものを複数が触らない）。GitHub API のレートにも注意（過剰並列を避ける）。

→ 並列の条件は **「素なファイル集合」かつ「素なリソース集合」**。どちらかを奪い合うなら直列化 or 各自に隔離環境。

## 原則
- **司令塔は実装しない**: メインの仕事は分配・監視・統合・判断。手を動かすのはエージェント。
- **ファイルもリソースも分ける**: worktree でファイルは分かれるが DB/ポート/スタックは共有。共有資源を奪い合う作業は並列にしない。
- **伝書鳩は貨物を運ばない**: 管理者が運ぶのは「ブランチ名・要約・合否・指示」。diff やレビュー全文を自分のコンテキストに抱えない（サブエージェント隔離を守る）。成果物はブランチにあり、レビュアーがそこを直接読む。
- **レビューは PR 上で資産化**: draft PR → 観点レビューをコメントで残す → 対応・resolve → `gh pr ready` で人間へ。指摘と対応が GitHub に残り資産になる。修正は同じエージェントを `SendMessage` で継続（文脈を保つ）。
- **沈黙は成功ではない**: 無音を順調とみなさない。心拍＋上限待機で「進んでいない」を検知する。
- **衝突する作業は並列にしない**: 速さよりコンフリクト回避。素なファイル集合に分けてから並列。
- **作るのは並列、統合は直列**: コンフリクトは1本ずつの統合で受け止める。
- **被弾したら rewind でなく clear**: メイン自身がツール呼び出し不能（生 XML 出力でターン停止）になったら `/rewind` を使わない（自分の編集ファイルだけ部分巻き戻しになり、巻き戻らない git commit/branch/worktree/push 済み PR と desync する）。`/clear`（記憶のみ消去・世界は無傷）してから世界（branch/PR）を見てやり直す。**やり直し/再 dispatch の前に対象 issue の既存 PR を `gh pr list` で確認**して二重作業を避ける（1ユニット=1 PR を保つ）。
- **管理者の学びも capture**: Sub-issue の学びは `yosage-dev-harness:implementer` が内包するが、**統合で判明した競合・ストール対処・横断判断**は司令塔（メイン）自身が `capture-learning` で蓄積する（誰が回すかは ルール `knowledge`。[[epic-implement]] と同じ切り分け）。
