# proposal — 壁打ちで提案書を作り、実装開始で凍結する

新規プロダクト/大きな機能の **起点** となる提案書を、ユーザーとの **壁打ち** で作る。
これは「企画の始まり」。詳細設計ではなく、**何を・なぜ・どこまで** を定める。

## 壁打ちは main セッションで（subagent ではない）
壁打ちはユーザーとの **対話的な往復** なので、隔離・一方向の subagent には向かない。
main セッションで対話しながら進める skill。発散→収束をユーザーと一緒に回す。

## 進め方
1. **発散**: 課題・目的・ターゲット・前提を、問いを投げて引き出す。曖昧な所は `AskUserQuestion` で確認。
2. **収束**: スコープ(MVP)と非スコープを切る。やらないことを明示。
3. **書き出す**: 下のテンプレで `.docs/proposal.md` を作る。
4. **次工程へ**: 固まったら `yosage-dev-harness:architect`(サブエージェント)でアーキ/方針へ、`document-architecture` で `.docs/architecture/` へ。

## テンプレート（`.docs/proposal.md`）
```markdown
# <プロダクト/機能名> 提案書
- Status: Draft        # Draft → Accepted → Frozen(実装開始) → Amended(例外時)
- Date: YYYY-MM-DD

## 背景 / 課題
## 目的 / 達成したいこと
## ターゲット / 利用者
## スコープ (MVP)
## 非スコープ（あえてやらないこと）
## 主要な仮説 / 前提
## 成功条件（どうなれば成功か）
## 大まかな進め方 / マイルストン
## 未解決の論点
```

## 凍結ルール（重要）
- **実装に入ったら `Status: Frozen`**。提案書は **書き換えないのが既定**。
- 設計の変化・詳細化は提案書ではなく **生きた doc**（`.docs/architecture` / `detail` / `api` / `ui`）へ反映する（→ `sync-design-docs`）。
- **よほどの方針転換**（前提が崩れた等）のみ提案書を改訂し、`Status: Amended` ＋ 変更理由・日付を残す。安易に直さない。

## 知見を残す（knowledge loop）
壁打ちでも設計判断は出る。recall（前）→ capture（後）で loop を回す。
- **前（起点）**: 過去の関連企画/知見を [[recall-knowledge]] で引くと、前提や落とし穴を踏みやすい。
- **後（凍結確定時）**: その過程で得た**再利用可能な知見**（判断基準・前提・落とし穴）を [[capture-learning]] で蓄積する（提案書は企画の起点を残すが、横断的に効く知見は別途 capture しないと残らない）。壁打ちは main セッションなので capture は **メイン自身**が回す（責務は ルール `knowledge`）。

## 原則
- **企画レベルに留める**: 実装詳細を書かない（それは architecture/detail）。
- **非スコープを明示**: スコープの境界が提案書の価値。
- **凍結を尊重**: 提案書は起点の記録。動くのは生きた設計 doc。
