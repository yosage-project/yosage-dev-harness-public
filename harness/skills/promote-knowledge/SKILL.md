# promote-knowledge — staged 知見をストアへ昇格する（明示実行）

staged なグローバル候補知見をまとめて精査し、ストアへバッチ PR する。**`/yosage-dev-harness:promote-knowledge` の明示実行でのみ動く**（`disable-model-invocation: true`）。recall・capture の最中に自動発火しない。

## 動的コンテキスト

staged な生層候補（`scope: global` かつ `status: active` の local entry。`global/` 配下＝ストアから同期済みのミラーは除外）。先頭2行に、設定ファイルを丸ごと開かずに取り出した要約（`workspace: true|false`・`knowledge.source: <値>`。writeOnly の項目は出さない）を出す。ワークスペース（設定の `workspace` が true）では自ストア ＋ 各 member repo（workspace 直下の子ディレクトリで `.git` を持つもの。ディレクトリ/ファイルいずれの型でも判定する）の `.claude/knowledge` を読み下ろして集約し、各行の先頭に由来（`.`＝自ストア／member ディレクトリ名）を付す:

!`yosage-dev-harness-promote-collect entries`

staged な蒸留層候補（あれば）。ワークスペースでは各 member の `criteria.global-proposed.md` も由来つきで列挙する:

!`yosage-dev-harness-promote-collect criteria`

## 起動条件

- 動かすのに要る最小 actionable 基準: 上記の staged 候補（生層 or 蒸留層。ワークスペースでは自ストア＋member 集約後の合計）が1件以上あること。**0件なら「昇格対象なし」を報告してここで終了する**（無理に空 PR を作らない）。
- ストア同期設定（`knowledge.enabled: true` ＋ `knowledge.source`）が無ければ昇格先が無い。停止して人へ報告する（`.claude/yosage-dev-harness.local.json` での設定を依頼する）。

## 1. 収集

- **判定**: 設定の `workspace` が true かで収集範囲を決める（`yosage-dev-harness-config-get workspace` の値。member 判定の基準は `yosage-dev-harness:librarian` 手順1と同一＝workspace 直下の子ディレクトリで `.git` を持つもの。ディレクトリ/ファイルいずれの型でも判定する）。
  - **ワークスペース**（`workspace: true`）: 自ストア ＋ 各 member repo を読み下ろして集約する。recall（`yosage-dev-harness:librarian`）が workspace で member INDEX を読み下ろす方向つきと対称(federation-aware promotion)。
  - **単一 repo**（`workspace: false`）: 従来どおり cwd の `.claude/knowledge` のみを見る(後方互換)。
- **生層**: 対象となった各 repo（自ストア／各 member）の `.claude/knowledge/<domain>/*.md` のうち frontmatter `scope: global` ＋ `status: active` の entry（雛形 `_entry-template.md`・`global/` 配下は対象外）。**各 entry の由来 repo（`.`＝自ストア／member ディレクトリ名）を控えておく**（手順9の move で cross-repo 削除に使う）。
- **蒸留層**: 対象となった各 repo の `.claude/review/criteria.global-proposed.md` の各提案項目（無ければ生層のみで進める）。こちらも由来 repo を控えておく。

## 2. 分類（検証の種類で束ねる）

候補をまとめて一律の指示で流さず、**候補ごとに「何を確認すれば正しいと言えるか」で分類してから**手順3以降を進める。分類軸は「どの技術の話か」ではない。分類する理由は2つ:

- 性質が違う候補を一律の指示で流すと、群固有の欠陥が検出されない（下表は実際に混在させて流した結果、群ごとに異なる欠陥が見逃された実例）。
- ストアの確認手段は人間レビューだけであり、一度に大量の判断を求めるとゲートが形骸化する。分類ごとに束ねてバッチを分けることで、レビューが一度に扱う判断の量を絞る。**件数で機械的に区切らない**（同じ分類なら1バッチにまとめてよい。分類が違えば件数が少なくてもバッチを分ける）。

以下は最小4分類。候補の性質がこれらに当てはまらない場合は、**「正しさを決めるもの」を自分で言語化してから**同じ形式で分類を追加してよい（分類名を技術領域で作らない）。

| 分類 | 正しさを決めるもの | 確認条件 |
|---|---|---|
| **外部要件由来**（規約・審査要件・法令等） | 原典に書いてあるか | 手順5（引用照合ゲート）で**主張が原典に支持されているか**を確認する。**出典 URL が生きていることと、主張を支持していることは別**（URL が到達可能でも該当記述が無いことがある）。 |
| **ライブラリ挙動由来**（実装・API の挙動） | どの版で観測したか | **確認した版を本文に記録する**（宣言された依存範囲ではなく、確認時に解決されていた実際の値）。散文として本文に書く（frontmatter への構造化は別途の議論に委ねる。決まればそちらの形式に合わせる）。版が上がったら再確認が要る旨も本文に残す。 |
| **手法・技法の記録** | 読者が再現できるか | 手順が具体的か、**前提条件が明示されているか**（どんな構成・状況で成り立つ手法か）、素直な方法では駄目な理由が書かれているかを確認する。 |
| **実装上の落とし穴**（「X ではなく Y で直す」型） | 他の解が誤りである理由 | **なぜ X では駄目かが仕組みとして説明されているか**、**Y が最適である前提**（画面構成・データ構造・版など）が明示されているかを確認する。前提が違えば別の解が正しくなるため、前提を書かずに結論だけ残さない。 |

分類は候補ごとに1つ選ぶ。複数の性質が混在する候補は、手順3の「案件固有の判断」チェックと同様に内容を分割してから分類する。

## 3. value gate（残す価値の判定）

各候補に、[[capture-learning]] の価値ゲート分類（「残す価値の判定＝base model への差分だけ」節）を適用し、「本当に全プロジェクトで成り立つか（base model への差分か）」を再判定する。

- **案件固有の判断が混入していないかを確認する**: 本文を読み、特定案件の設計判断（画面構成・アーキ構成・特定プロダクトの制約等、他所では成立しない前提）が一般的な結論と同居していないかを見る。これは [[capture-learning]] の「書き込み前の自己チェック」（正本 ルール `knowledge`）が capture 時点に問う観点を、**昇格時点の最後の砦として再度確認する**もの（正本の「書き込み前の自己チェック」節が「昇格時点の確認とは別軸」と述べるとおり、capture 時点の自己チェックをすり抜けた混入を拾う役割であり、同じ検査を重複させるものではない）。
  - **混入なし** → 通常どおり通過/見送りを判定する。
  - **混入あり** → **部分昇格**する。一般部分だけを手順4以降でストアへ出し、案件固有の適用部分は手順9（move）で独立した `scope: local` entry として書き直して残す（[[capture-learning]] の「昇格＝move」規則が言う「1 entry を半分 global・半分 local にしない」の適用）。**書き直しの元ネタは、混入が見つかった元の entry ファイルそのもの**（ローカルの `.claude/knowledge/<domain>/` に置かれた原本）。**手順4（de-localize）以降は原本を直接編集せず、複製した作業用コピーに対して行う**（一般部分の抽出・de-localize・引用照合はすべて複製側で行う。命名は原本と混同しない形にする）。原本は変更せずそのまま残し、手順9で局所版へ書き直すまで（ストア PR がマージされるまで日単位で掛かりうる間も含めて）いつでも元の全文を参照できる状態を保つ。
- **通過** → 手順4（de-localize）へ進む。
- **見送り（decline）** → boolean フィールドは足さない。[[capture-learning]] の promote-on-recall（decline）と同じ扱いで、entry の `scope` を `local` へ戻し、本文に**反証可能な理由**（何が崩れたら昇格可になるか）を追記する。理由が entry の内容と食い違えば次回 recall で自然に再浮上する（新しいライフサイクル状態は持ち込まない）。

## 4. de-localize（中核ゲート）

travel 面（ストア entry）へ出す前に、home-repo 固有参照を除去・置換する。判定基準の正本は ルール `knowledge` の「書き方不変: travel 面の自己完結」節（本 skill では再掲しない）。**手順3で部分昇格と判定した候補は、この手順以降を作業用コピーに対して行う**（手順3の指示どおり原本は編集しない）。ここでは実行手順のみ:

1. **裸 `#N`・`owner/repo#N`・repo/org identity を除去**: 番号が指す経緯を実体の説明文に書き換える（例:「pre-commit フックで secret 検出を実装した際に判明した」のように、番号を消しても分かる形にする）。耐久リンクが要るなら外部 URL に置き換える。
2. **固有名・専有名を汎用概念名へ**: プロダクト名・社内ツール名・チーム名などを一般的な役割名（例:「グローバル知識ストア」「配布ハーネス」）に置換する。**第三者ライブラリ名・API 名・バージョン番号は対象外（剥がさない）**: これらは home repo 固有の参照ではない（ルール `knowledge` の「home repo 固有パスと配布 payload パスの区別」節と同型の切り分け＝剥がすのは home repo 固有の参照だけ）。剥がすと手法・挙動が再現できなくなる。
3. **非配布 path 参照の除去（配布 payload パスは剥がさない）**: `.docs/` など非配布ディレクトリへのパス引用があれば、内容をインラインで要約するか除去する。内部の `path` 根拠ハンドルも、home repo 固有のソースパス（このリポ特有のファイル）は home repo 外では再解決できないため、判断の実体説明の一部として書き直すか削る。**ただし配布 payload のパス（正本 ルール `knowledge` の「home repo 固有パスと配布 payload パスの区別」節が挙げるパターン）は剥がさず取っ手として残す**。取っ手を持てないエントリも、それを理由に昇格を block しない（同節「取っ手は必須にしない」）。
4. **相互参照の解決確認**: 候補本文がストアに存在しない他エントリ（同一バッチで見送りになった候補・ローカルにしか無いエントリ等）を参照している場合、その参照を宙に浮かせない。参照先の内容を本文へ展開するか、参照そのものを落とす。
5. **実体インライン検証**: 1〜4を終えた後、番号・固有名・非配布パスを一切開かずに「判断・なぜ・適用」の3点が読めるか読み直す（配布 payload パスと第三者ライブラリ名・API 名・版は開いてよい取っ手なので対象外）。読めなければ書き直す（このセルフチェック自体がゲート）。

## 5. 引用照合ゲート（`source:` を持つ候補）

value gate（手順3）と de-localize（手順4）は「残す価値があるか」「travel 面で自己完結するか」を問うが、どちらも**主張の真偽・引用の正確さ**は問わない。真偽軸の共通手順の正本は ルール `knowledge` の「書き方不変: 引用照合ゲート」節（本 skill には再記述しない）。`source:`（外部出典 URL）を持つ候補はここでその手順を実行してから手順6（ストア clone）へ進む。`source:` を持たない候補（内部接地＝`path` ＋ 安定ハンドルで grep 再解決できる）はこの手順の対象外。

**外部要件由来（手順2の分類）は特に重点的に確認する**: URL が到達可能であることは、主張を支持していることの証明にならない。到達できても該当記述が見当たらない場合は「照合不能」ではなく「原典に無い主張」として扱う。

**昇格時点固有の帰結**（正本の分岐を、この着火点でどう扱うか）:
- **一致** → 手順6（ストア clone）へ進む（`checked:` の更新は正本の手順のとおり）。
- **原典に無い主張・存在しない見出し名・存在しない引用**（正本の「止める」）→ **この着火点では昇格しない**。エントリを原典に合わせて訂正するか、支持されない記述を削るまで手順6へ進まない。
- **原典と矛盾する主張**（正本の「止める」を昇格時点でさらに具体化）→ **昇格を止めて人間へ差し戻す（loud 停止）**。矛盾の内容（原典の該当箇所の引用 vs エントリの主張）を人間へ報告する。**候補を静かに `scope: local` へ降格しない**（誤りが訂正されないまま放置されうるため）。人間が原典に合わせてエントリを訂正してから、この手順からやり直して再昇格する。
- **照合不能**（URL が到達不能・記述の有無が確認できない。正本の「止める」を昇格時点でさらに具体化）→ **この着火点では昇格しない**。**到達不能である旨と試みた URL を人間へ報告する**。確認が取れるまで昇格せず、手順6へ進まない。

## 6. ストア clone（dedup・PR 共通の下準備）

1. **ストア設定を解決**: `.claude/yosage-dev-harness.local.json` の `knowledge.source`/`knowledge.ref`（`yosage-dev-harness-config-get knowledge.source` 等で取り出す）。
2. ストアをローカルへ一時 clone しブランチを切る（以降の手順7・8はこの clone に対して行う）:
   ```
   git clone --depth 1 --branch <ref> <source> <tmp-dir>
   cd <tmp-dir> && git checkout -b knowledge/promote-<date>
   ```

## 7. dedup

手順6で作成したストア clone の `knowledge/<domain>/` を検索し、重複が無いか確認する。

- 実効 id の解決: エントリに `id:` frontmatter が無ければ、ファイル名の slug（拡張子を除去し、先頭の `YYYY-MM-DD-` プレフィックスがあれば除去した残り）がそのエントリの実効 id。
- 同 id が既にある → `supersedes` を付けて更新版として提出する。
- 別 id だが内容が実質同じ → 統合を提案する（重複のまま両方出さない）。
- 完全自動の dedup はしない。**最終ゲートはストア PR のレビュー（人間）**。ここでの確認は明白な重複の事前フィルタに留める。

## 8. ストアへのバッチ PR

1. de-localize 済みの生層 entry ファイルを**そのまま** `knowledge/<domain>/` へ配置する。**`INDEX.md` は含めない**（consumer 側の生成物。ストア側でも手編集しない）。
2. de-localize 済みの蒸留層項目を `review/criteria.md` へ**追記**する（既存内容の上書き・削除はしない。追記前に重複が無いか見る）。
3. コミット → push → `gh pr create --repo <owner>/<store> --base <ref> --head <branch> --title "<title>" --assignee @me --body-file <file>` で PR 作成。**手順6で一時 clone した文脈からは `gh` のブランチ auto-detect に頼らず、`--repo`/`--head` を明示する**（clone 直後の tracking 状態依存で auto-detect が失敗し、push 自体は成功していても `aborted: you must first push the current branch to a remote, or use the --head flag` になることがある）。同じ理由で **`--title` も明示**する（`--title`/`--body`/`--fill` のいずれも無いと `gh` が対話プロンプトに入り、非対話実行では失敗する）。`--assignee @me` で作成者を assignee にする。ストアのブランチは設定 `knowledge.ref`（既定は `main`。ストアに合わせて変えられる）で、`--base <ref>` はそれに従う。ストアは release タグを切らない独立した知識専用リポ。ストア自身の README に明記された規約（ブランチ・マージ方式）に従う。PR 本文は `--body-file` 経由で渡す（本文中の markdown バッククォートによるシェル置換事故を防ぐ）。self-contained に書く（何を・なぜ昇格するか、対応する候補一覧、手順2の分類・value gate / de-localize / 引用照合ゲートを踏んだ旨）。
4. ストア側の受け入れは**人間の PR レビューが唯一のゲート**（自動マージしない）。

## 9. move（PR マージ後）

PR がマージされたことを確認してから（`gh pr view <PR番号> --repo <owner/store> --json state` の `MERGED`、または人間からの確認）実行する。マージ未確認のまま move しない。

昇格した各 entry について、[[capture-learning]] の「昇格＝move（コピーではない）」規則に従い、ローカルの昇格元 entry を削除する。蒸留層は取り込んだ `criteria.global-proposed.md` の該当項目を削除する。project 固有の適用が別途要るなら、独立した `scope: local` entry として書き直して残す（ストアの一般版とは別物。1 entry を半分 global・半分 local にしない）。

手順3で部分昇格と判定した候補は、ここで初めて原本（手順3以降ずっと変更せず保持してきたもの）を書き直す。**削除ではなく書き直し**である点が通常の move と異なる:「昇格＝move」規則は消える（削除される）ことを前提にしているが、部分昇格では一般部分だけが消え、案件固有部分は残る必要があるため、原本を案件固有部分だけの `scope: local` entry に置き換える。**この書き直しが完了し保存されるまでは原本を削除しない**（書き直しに失敗した場合に備え、案件固有部分が消えたまま原本だけ消えるという事故を避ける）。書き直しが完了して初めて、一般部分の内容がローカルから消えたことになる。

**workspace モードでの cross-repo 化**: 手順1で控えた由来 repo ごとに削除を分ける（昇格元の削除が複数 member repo をまたぐため、1回の操作では終わらない）。

- **自ストア（`.`）由来**: 通常どおりこのリポジトリのローカル変更として削除・コミットする。
- **member repo 由来**: **その member repo の中で**削除する（workspace ルートから直接 member 配下のファイルを削除コミットしない。各 repo の変更はその repo 自身の履歴に属する）。`INDEX.md` の再生成は**任意**（`yosage-dev-harness-knowledge-index .claude/knowledge` を member 配下で実行）——ローカル索引は追跡されず recall も直接列挙が主経路なので必須の手順ではないが、人が手元でファイルを開く際の利便性としては残る（ルール `knowledge` の「ローカル索引は任意のキャッシュ」節）。削除は各 member の標準 PR ループ（ルール `pr-loop`。draft → 一次レビュー or 自己レビュー → `gh pr ready` → 人間マージ）に乗せる。entry 削除のみの変更なので Direct 相当（自己レビューで代替可）。
- 全 member の削除が終わったら、今回のバッチで drain した entry と repo の対応を人へ簡潔に報告する。

## 溜まったら回す

staging（`scope: global` entry・`criteria.global-proposed.md`）は capture 時点では PR されず貯まるだけなので、ある程度溜まったら本スキルを**明示実行**してドレインする（pull 型のリマインドは持たない。忘れても壊れない＝反映が遅れるだけ）。

## 原則

- 明示実行のみで動く。他の skill・recall からは起動しない。
- ストアへの反映は常に人間の PR レビューが最終ゲート。自動マージはしない。
- de-localize を省略しない（travel 面の自己完結が崩れたエントリはストアへ出さない）。
- `source:` を持つ候補の引用照合ゲートを省略しない（原典と矛盾するエントリは止めて人間へ差し戻す。静かに降格しない）。
- 検証の種類による分類を省略しない（技術領域で束ねない。分類ごとの確認条件を飛ばさない）。
