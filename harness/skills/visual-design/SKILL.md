# visual-design — 既定解に流されず、対象に固有の視覚デザインを起こす

視覚デザイン（色・書体・レイアウト・signature）を、**対象（subject）に接地したトークン系を先に立ててから批評し、作る**スキル。
「ソフトウェア設計」（仕組みをどう作るか）とは別レーン。二義性の解消・視覚レーンへの入口判定・儀式の重複回避は [[visual-design-routing]] が正本（本スキルは名前参照のみ、再記述しない）。

## いつ使うか
- UI・ページ・コンポーネントの見た目（配色・タイポグラフィ・レイアウト）を新規に起こすとき
- 既存の見た目を作り直す（リブランド・リデザイン）とき
- 「テンプレっぽい」「AI が作ったっぽい」見た目を避けたいとき
- 逆に、仕組み・アーキテクチャの判断（ビルド基盤選定・コンポーネント設計・状態管理方式など）には使わない（`deliberate-design`/`grounded-design` へ）

## 0. 着手時の recall（層状 recall・必ず先に）

[[recall-knowledge]] を名前参照して、以下の2層を引き込む（ルール `knowledge` の recall/capture 規律に従う。ポリシーはここに再記述しない）:

- **local**（`ui/` domain）: このプロジェクト固有のブランドトークン・コンポーネント様式・過去のデザイン判断。無ければ「無し」でよい（初回はここが空でも進める）。
- **global**（sync 済みのベストプラクティス知識）: モデルが持たない非自明な craft カタログ（後述「AI 既定解カタログ」を含む）。腐っていれば fix-on-recall でその場を直す。

教科書的定石（後述「外部定石」節）は knowledge に無くてよい。モデルの一般知識＋本スキル本文の直接引用でまかなう（価値ゲート）。

## 1. プロセス（2パス: 立てる → 批評する → 作る → 自己批評）

### (a) 対象（subject）に接地する
ブリーフが対象・オーディエンス・そのページの果たす仕事を確定していなければ、自分で確定してから進める:
具体的な対象を1つ名指し、オーディエンスと「このページの唯一の仕事」を明言する。対象自身の世界（素材・道具・語彙）が固有の選択の源泉になる。ブリーフの実際の内容・題材を通して作る（一般論のプレースホルダで作らない）。

### (b) トークン系を先に立てる（ブリーフから・実装より前）
以下4種のトークン系を、コードを書く前にコンパクトに立てる:

- **色**: 4〜6個の named hex 値で記述する。
- **書体**: 最低2ロール（display・body）。データやキャプション用の utility ロールが要れば3つ目を足す。display は抑制して使う特徴的な書体、body は補完する読みやすい書体。
- **レイアウト**: 1文プローズ記述 ＋ ASCII ワイヤーフレームで発想・比較する。
- **signature**: このページが記憶される唯一無二の要素。ブリーフを適切な形で体現するもの。

### (c) ブリーフと照らして批評する（既定解ゲート・コードを書く前に必ず）
立てたトークン系の各部分が、**「同種のブリーフに対して自分が毎回出しそうな既定解」になっていないか**を自問する（似たプロンプトを頭の中で流し、同じ所へ収束しないか検証する）。

判定の土台として、[[recall-knowledge]] で引いた「AI 既定解カタログ」（global knowledge・非自明なので本文に焼かない）を参照する。ブリーフがその見た目を明示的に要求しているなら、既定解であっても正当（**ブリーフの言葉が常に勝つ**）。ブリーフが自由に残した軸だけを、既定解に費やさない。

既定解に一致し、かつブリーフがそれを要求していない箇所は、対象固有の選択に revise し、**何を変えたか・なぜかを明示**する。この批評を終えてから初めてコードを書く。

### (d) build
revise 済みのトークン系に厳密に従って実装する。色・書体の判断はすべてトークン系から導出する（その場の思いつきで足さない）。stack 非依存の craft・トークン設計に徹し、実コードの書き方（フレームワーク選択・コンポーネント分割規約・テスト方針）は consumer 自身の coding/test ルールへ委ねる（本スキルはフレームワークを指名しない）。

CSS を書く場合、セレクタの詳細度が意図せず打ち消し合わないよう注意する（型ベースセレクタと要素ベースセレクタが混在するセクション間の余白などで起きやすい）。

### (e) 自己批評（build 後・必ず行う）
- **boldness は1箇所に集中**させる（signature 要素）。それ以外は静かに保つ。ブリーフに奉仕しない装飾は削る。
- **"remove one accessory"**: 出す前に一歩引いて見直し、無くても成立する装飾要素を1つ削れないか確認する。
- 装飾（構造的な番号・見出し・罫線を含む）は**内容の真実を符号化する時だけ**使う。例: 番号マーカー（01/02/03）は本当に順序が読者に意味を持つ（実プロセス・型付きタイムライン等）ときだけ使う。順序に意味が無いなら使わない。
- 環境がレンダリング・スクリーンショット取得に対応するなら、実際に見て自己批評するとよい（任意ステップ。consumer にレンダ環境が無い場合もあるため必須にはしない。既存のブラウザ自動化・検証手段があればそれを使う）。
- **正本へ確定する前に人間の目視確認を挟む（上記の自己批評とは別の必須ステップ）**: レンダリング・スクリーンショット取得に対応する環境では、自己批評まで終えたビルドを実際に可視化（Artifact・ブラウザプレビュー等）し、**正本ドキュメント・最終コードとして書き込む前に人間へ提示して明示的な確認を得てから**先へ進む。トリガは「build を終えたこと」ではなく「その内容を正本として確定させようとする直前」であり、確認が得られるまでは正本への書き込み・コミットを行わない。会話中の細かい調整案の提示にはこの確認を求めない（求めると軽微な調整にも過剰な儀式が発生するため、正本として確定させる場面に限定する）。これは「## 2. 発散の提示形」（複数方向のうちどれを選ぶか）とは別軸——単一方向で進める既定ケースでも適用する。レンダリング手段が無い consumer では、この確認ステップは適用できないため求めない（直前の自己批評ステップと同様、任意扱いのまま）。**この任意化条件を、委譲先ワーカー個体がレンダリング・人間確認の手段を持たないだけの場合に誤って適用しない**（`yosage-dev-harness:implementer` のように委譲先ワーカーがこの確認を実行する手段を持たない場合でも、dispatch 元はその手段を持ちうる。任意化条件が指すのは consumer 環境全体にレンダリング手段が無い場合であり、委譲先ワーカー個体の手段の有無とは別軸）。委譲先ワーカーがこの必須ステップを満たせない場合の扱いは `yosage-dev-harness:implementer`（正本へ確定する前に停止し、確認が取れてから再開する規律）を名前参照する（同じ規律をここへ再記述しない）。

### 品質フロア（すべてのビルドで満たす）
- モバイルまでレスポンシブ。
- キーボードフォーカスが視覚的に確認できる。
- `prefers-reduced-motion` を尊重する。

## 2. 発散の提示形（既定は単一方向・ブリーフに自由度があれば任意で複数方向）

既定は**単一方向＋強い批評ゲート**（上記(c)）で進める。ブリーフが視覚方向を指定せず自由度が大きい場合は、任意で2〜3の視覚方向（トークン系の異なる組み合わせ）を提示し、人間に選ばせてよい。美的な良し悪しは客観的なスコアで裁定できないため、収束は人間が見て選ぶ（human-in-the-loop）。既定解回避を担うのは複数方向の発散そのものではなく、**(c) の批評ゲート**である点に注意する（発散はあくまで任意の追加ステップ）。

## 3. このレーンは討議儀式を踏まない

[[visual-design-routing]] の定めにより、視覚デザインでは `deliberate-design` の多案比較＋二軸レビューは行わない。上記 (c) の批評ゲートが既定解回避を担っており、討議儀式を重ねると二重になる。

## 4. 確定したら knowledge へ capture

[[capture-learning]] で `ui/` domain（consumer 固有＝ローカル）に、このプロジェクトで確定したブランドトークン・コンポーネント様式・デザイン判断を残す。教科書的定石や汎用カタログ（モデルが既に持つ一般論）は残さない（価値ゲート）。

## 帰属

本スキルの craft プロセス（2パス構造・トークン先出し・既定解批評ゲート）は、公式プラグイン `frontend-design`（Anthropic / Prithvi Rajasekaran・Alexander Bricken、Apache-2.0）を着想元とし、上記の外部定石にも接地して独自に書き起こしたもの。逐語コピーではない。

## 原則
- **トークンが先、コードは後**: 色・書体・レイアウト・signature を固めてからでないと、批評しようがない。
- **既定解は選択ではない**: 対象を問わず出るなら、それは既定であり選択ではない。ブリーフの言葉が明示的に望まない限り、自由な軸をそこに費やさない。
- **boldness は1箇所**: 冒険は signature に集中させ、それ以外は静かに保つ。
- **人間が見て選ぶ**: 美的品質はスコアで裁定できない。複数方向を出したら人間の選択に委ねる。
