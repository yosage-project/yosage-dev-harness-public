# grounded-design — 憶測で設計しない（逸脱・ハルシネーション・無自覚な補完の対策）

設計やアーキ判断、既存コードに触れる実装では、**内部（コードベース）と外部（言語/FWの定石）の両方に接地(ground)してから**書く。
断つべき失敗は3つ: **①既存実装からの逸脱**、**②ハルシネーション**（実在しないものの参照）、**③外部ベストプラクティス/仕様からの逸脱・無自覚な補完**（仕様に無い部分を埋めたのに見えないまま実装に入る）。

> **補完は禁止しない**。知識を補う補完はむしろ歓迎。ただし**補完するなら根拠ラベルつきで明示**し、ユーザーが「補完・前提」だけ見て前さばきできるようにする（後出しの1問1答を減らす）。

## 鉄則
1. **読んでから参照する**: 開いて確認していないファイル/関数/メソッド/APIの引数/DBカラム/設定キーを、名前で出さない。
2. **根拠ラベルを必ず付ける**: 設計判断・外部参照には「何に接地したか」を印で示す。**ラベルの無い具体名・断定は書かない**（最大の防壁）。
   - ラベルの定義（`✓内部`/`✓外部`/`✓実測`/`§仕様`/`≈慣例`/`+補完(要確認)`/`⚠内部≠外部(要判断)`）は **ルール `grounding-labels`（常時オンの正本）**。
   - **要確認**（`+補完(要確認)`・`⚠内部≠外部(要判断)`）は後述「## 補完・前提（要確認）」に必ず一覧化。`⚠内部≠外部` は両方を出典つきで併記し、**黙ってどちらにも倒さず人間の判断を仰ぐ**。
3. **前例を先に探す**: 似た機能・層・パターンの既存実装を2〜3件特定し(`Grep`/`Glob`/Explore)、`path:line` で引用。**それに倣う**のが既定。
4. **外部にも接地する（読んで決着するか／動かさないと決着しないかを判定する）**: 言語/FW の慣例・仕様に関わる判断を、自分の事前知識だけで断定しない。裏取りの前に、その主張が**読めば決着する**（コード/doc・外部の定石や仕様を当たれば答えが出る）のか、**動かさないと決着しない**（このリポジトリ・このシステム自身の実行時の振る舞いに関する主張。例:「〜という理由で失敗している」「基点は実行時に〜になる」）のかを見分ける。
   - **読んで決着する主張**: 不確かなら `yosage-dev-harness:researcher`（出典つき digest を返す）で裏取りして `✓外部`/`§仕様` にする。接地できなければ `+補完(要確認)` のまま残す（嘘で埋めない）。
   - **動かさないと決着しない主張**: **`yosage-dev-harness:researcher` では裏取りできない**（外部出典もコードの読解も、実行時に何が起きるかへの答えを持たない）。実際に動かして観測し、`✓実測 <観測構成>` にする。未検証のまま進めるなら `+補完(要確認)` のまま「## 補完・前提（要確認）」節へ残す。
   - **報告に書かれた原因は接地ではない**: バグ報告・issue の記述は症状（観測された挙動）については一次情報だが、**原因の説明は主張**。報告文をそのまま `✓内部`/`✓実測` として扱わない（自分で読む/動かして確認するまでは `+補完(要確認)`）。
   - **検証が重い場合**: 主体の判断で検証を独立した issue として切ってよい（人間の裁可を待たない）。ただし**未検証のまま、その主張に依存する受け入れ条件を確定させない**（検証を切り出したら、依存する条件も検証結果待ちとして残す）。
5. **逸脱・食い違いは明示**: 勝手に決めず書き出す。
   - 既存パターンから外れる → `逸脱: <何を変えるか> / 既存: <今のやり方 path:line> / 理由: <なぜ正当か>`
   - **内部と外部が食い違う → `⚠内部≠外部(要判断)`**: `内部: X（path:line）／外部BP: Y（出典）／トレードオフ: …` を併記し人間判断へ。軽微なら内部踏襲（一貫性優先）でよいが、本質的な食い違いは黙って倒さず surface。
6. **不確実は不確実と書く**: 埋められない箇所を尤もらしい嘘で埋めない。`+補完(要確認)` / `TODO(要確認)` を残す。

## 手順
### Step 0. 接地（設計を書く前に必ず・内部＋外部）
- **蓄積済み知識を取り寄せる**: [[recall-knowledge]] で、このドメインの過去の判断・落とし穴を index から選り分けて読む。
- **内部接地**: 関連する既存実装を探索し、**前例リスト**を作る（`path:line` + 1行説明）。広い横断調査は `yosage-dev-harness:explorer` サブエージェントに委譲してもよい。規約の正本（`.docs/`、`.claude/rules/<該当パス>`、CLAUDE.md）を確認。命名は `glossary` に従う。
- **外部接地**: 言語/FW の**ベストプラクティス・定石・仕様の制約**に照らす。事前知識で確信が持てない外部慣例は **`yosage-dev-harness:researcher`** で出典つきに裏取りする（特に「補完しようとしている」部分）。
- 使う予定の外部シンボル/APIの**実体**を開いて、シグネチャ・型・引数を確認。
- 接地が薄いまま設計に進まない。情報が足りなければ取りに行く（just-in-time）。

### Step 1. 設計を書く（ラベルつき）
- ドキュメント化する場合は [[design-doc]] に従い **設計 issue** に書く（本文テンプレに沿う。設計を書いたファイルを `.docs/` の中に作らない）。
- 各技術的主張に**根拠ラベル**（鉄則2）。前例の引用と、逸脱/食い違いの明示を含める。
- **末尾に「## 補完・前提（要確認）」節を置く**: `+補完(要確認)`・`≈慣例`・`⚠内部≠外部(要判断)` を箇条書きで一覧化（**`⚠内部≠外部` を筆頭に**）。ユーザーはここだけ見て前さばきできる。該当が一つでもあれば必ず置く。**何も無ければ「（なし）」と明記**（形骸化させない）。

```markdown
## 補完・前提（要確認）
- ⚠内部≠外部(要判断): <論点> — 内部: X（path:line）／外部BP: Y（出典）／どちらに倒すか要判断
- +補完(要確認): <仕様に無く埋めた点> — 根拠: <なぜそう埋めたか／未接地>
- ≈慣例: <採用した慣例> — 別解: <あれば>
```

### Step 2. 自己点検（提出前チェックリスト）
- [ ] 具体名(ファイル/関数/API/カラム)・設計判断は全て**鉄則2のいずれかのラベル**（定義は ルール `grounding-labels`）が付いているか（**ラベル無しの断定が無いか**）
- [ ] 外部慣例/仕様に関わる判断を、事前知識で断定せず接地したか（不確かは `yosage-dev-harness:researcher`）
- [ ] 似た既存実装を引用し、踏襲 or 逸脱理由を述べたか
- [ ] **内部と外部が食い違う点を `⚠内部≠外部` で surface したか**（黙って倒していないか）
- [ ] **「## 補完・前提（要確認）」節に補完/慣例/食い違いを一覧化したか**
- [ ] 既存の `.claude/rules` / `.docs` と矛盾していないか

### Step 3. 意味的レビュー（任意・重要設計時）— 内部軸 ＋ 外部軸の二枚
別主体に懐疑させて、設計を書いた自分の盲点を破る。**2つを並走**させ、verdict は**混ぜずに**受け取る:
- `yosage-dev-harness:consistency-reviewer` — **内部軸**: 「実在しない参照」「既存パターンからの逸脱」。
- `yosage-dev-harness:best-practice-reviewer` — **外部軸**: 「言語/FW の定石・原理原則から外れた劣った型・車輪の再発明・既知のアンチパターン」。過信由来の非定石をここで実装前に止める。版依存は yosage-dev-harness:researcher で裏取りさせる。

二軸は**違う問いに答える**ので正反対を指すことがある（既存パターン自体が劣るとき＝内部「合わせろ」／外部「外せ」）。これは事故でなく**拾いたい信号**。両者の生の指摘と食い違い点を受け取り、**呼び出し元が裁定する**（一票に均さない）。食い違いは鉄則5の `⚠内部≠外部(要判断)` として surface し、次で分岐（＝鉄則2/5 の「人間判断を仰ぐ」をここで精緻化する。`⚠` の全件が人間行きではなく、**判断が要るのは前例なき価値トレードオフだけ**で、客観的欠陥は判断でなく標準に倒すだけ）:
- **客観的欠陥**（外部レビュアの「欠陥」ラベル＝正確性・名指しアンチパターン等、トレードオフでない）→ **標準に寄せて直す**（人間に上げない）。
- **価値トレードオフ**（「トレードオフ」ラベル）→ recall（[[recall-knowledge]]）が**この食い違いを直接裁定する知見**を持つか:
  - 持つ（過去の `scope: local` 逸脱判断／当該パターンを名指した定石エントリ）→ それを適用して裁定。
  - 持たない（前例なし）→ **人間に判断を仰ぐ**（黙ってどちらにも倒さない）。裁定結果は Step 4 で知見化＝次回は「持つ」側に移る。
  - 緩く関連するだけのエントリを「持つ」に引き伸ばさない。迷えば人間へ。

### Step 4. 確定したら知見を残す（loop を閉じる）
- 設計が確定したら、その過程で得た**再利用可能な知見**（判断基準・パターン・制約・落とし穴）を [[capture-learning]] で蓄積する。
- Step 0 の recall と対。**recall（前）→ capture（後）** で knowledge loop を閉じる（誰が回すか・省略不可は ルール `knowledge`）。

## 原則
- **接地 > 速度**: 内部にも外部にも接地するほど手戻りが減る。
- **嘘より空白**: 自信が無いなら、もっともらしく埋めず `+補完(要確認)` ＋ 補完・前提節に出す。
- **既定は踏襲、逸脱は説明責任**: 一貫性がデフォルト、外す/食い違うなら理由を残し、必要なら人間に判断を仰ぐ。
- **補完は歓迎・ただし可視化**: 補完で知識を補うのは良い。隠さず根拠ラベルで surface する。
