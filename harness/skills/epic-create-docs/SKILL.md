# Create Epic Docs Skill

Epic の計画策定フェーズで `.epic_docs/` にドキュメントを作成するスキル。
調査→現状分析→設計→Sub-issue 分割までを `.epic_docs/` にまとめる。

## 前提

- `.epic_docs/` は Epic 用ドキュメント置き場（CLAUDE.md に記載）
- 最終的な設計内容は GitHub Issue 本文に全量記載するため、ここはあくまで **計画策定の作業場**
- Issue 作成は別スキル (`epic-create-issues`) で行う
- 調査・方針設計・Sub-issue 分割の検討は `yosage-dev-harness:architect`(サブエージェント)に依頼し、その digest を基にまとめると効率的（特に既存実装の「機能検討→Epic化」）。新規プロダクトは `.docs/proposal.md`(凍結) → yosage-dev-harness:architect → ここ、の順
- **`.epic_docs/` の置き場は cwd 固定ではない**: 複数リポジトリが同居するワークスペースでは、`.epic_docs/` を実装先リポジトリの外（ワークスペース側リポジトリ）に置く運用がある。置き場は「cwd から上へ辿って見つかる最も外側の git リポジトリの直下」。単一リポジトリの導入先では自分自身が最も外側になるため、従来どおり cwd 直下が置き場になる（後方互換）。

## 手順

### 1. 置き場の特定・既存の `.epic_docs/` を確認

```bash
EPIC_DOCS_ROOT="$(yosage-dev-harness-epic-scope-resolve outermost-root)/.epic_docs"
ls "$EPIC_DOCS_ROOT/"
```

既存の Epic ドキュメントのフォーマットを把握する。特に `00_overview.md` の構成を参考にする。
以降の手順の `.epic_docs/` はすべて `$EPIC_DOCS_ROOT/` を指す（cwd 直下ではない）。

### 2. ディレクトリ作成

```
$EPIC_DOCS_ROOT/<epic-name>/
├── 00_overview.md          # 全体概要・Sub-issue 一覧
├── phase0/                 # Phase 0: 基盤整備
│   ├── 0-1_<sub-issue>.md
│   └── 0-2_<sub-issue>.md
├── phase1/                 # Phase 1: メイン作業
│   ├── 1-1_<sub-issue>.md
│   └── ...
└── phase2/                 # Phase 2: クリーンアップ
    └── 2-1_<sub-issue>.md
```

Phase の数は Epic の規模に応じて調整する。小規模なら Phase 分割不要。

### 3. 調査・分析

ユーザーが提示した概要に基づき、コードベースを調査する：

- 対象コードの現状把握
- 問題点の洗い出し（具体的なファイル名・行番号・コード例を記録）
- 影響範囲の特定
- 既存のパターンや規約の確認

**重要**: 調査結果は具体的に記録する。「~70箇所」のような概算ではなく、可能な限り対象ファイルを列挙する。

### 4. `00_overview.md` の作成

以下の構成で作成する：

```markdown
# <Epic タイトル>

## 目的

<何を達成するか>

## 現状の問題

<調査結果に基づく問題点の整理>

## 変更スコープ

| # | 項目 | 概要 |
|---|------|------|

## 方針

<技術的な方針・制約>

## Sub-issues 構成

### Phase 0: 基盤整備
| Sub-issue | 内容 | 依存 | 取り込み先 |

### Phase 1: メイン作業
| Sub-issue | 内容 | 依存 | 取り込み先 |

### Phase 2: クリーンアップ
| Sub-issue | 内容 | 依存 | 取り込み先 |

(取り込み先の列は「Epic ブランチ」か「既定ブランチ（理由）」。判断は手順6の「Sub-issue ごとの取り込み先」に従う)

## 実施順序

<依存関係グラフ>

## ブランチ命名

<epic/<epic名> から切るブランチ一覧>

## スコープ外

<今回やらないことの明示>
```

### 5. 各 Sub-issue ドキュメントの作成

各 Sub-issue について以下の構成で作成する：

```markdown
# #<番号> <タイトル>

## 概要

<何をするか>

## 対象ファイル

- `<ファイルパス>`（新規 or 修正）

## 実装内容

<具体的な変更内容。コード例を含む>

## 依存関係

- #<番号>（<理由>）

## 取り込み先

<Epic ブランチ ／ 既定ブランチ（理由）>

## 検証方法

<確認コマンド・手順>
```

`## 実装内容` は「具体的な変更内容」だけでなく、方向性の散文説明で済ませない。実装者（`yosage-dev-harness:implementer`
サブエージェント）は issue 本文だけを頼りに実装し、会話の文脈を持たない。次の観点を検討し、
該当するものは含める（機械的に全部足す必要はないが、検討せず散文の説明だけで確定させない）:

- 新規に定義する型・スキーマ・関数シグネチャは、実際の記法で書く（疑似コードや「〜のような」といった
  言葉での説明で済ませない）
- 分岐条件（成功/失敗/エッジケース）を列挙し、それぞれの処理を書く
- 既存コードとの接続点（呼び出し元・呼び出し先）を、具体的なファイルパス・シンボル名で示す

`## 検証方法` は「確認コマンド・手順」だけでなく、正常系をなぞるだけの条件にしない。正常系だけの条件は、
条件を書いた人と実装する人が共有している盲点を素通しする。次の観点を検討し、該当するものは条件に
含める（機械的に全部足す必要はないが、検討せず正常系だけで確定させない）:

- 統合された構成で観測する（成果物が存在することではなく、実際に動かして外から応答が返る・効果が
  観測できることを条件にする。単体構成で「ファイルが存在する」を満たしても、この観点は満たさない）
- 両方向（既定値が効くこと・上書きが効くことの両方。片方だけだと、もう片方が壊れていても気づけない）
- 失敗するべきときに実際に失敗すること（不正な入力で通らないことを観測する）
- 2回目の実行でも壊れないこと
- 状態が残っていない環境（クリーンな clone・再起動後）でも通ること

### 6. Sub-issue ごとの取り込み先の判断と Epic ブランチを作る条件

Sub-issue に分割したら、**ハーネスが Sub-issue ごとに取り込み先を判断**し、`00_overview.md` の表の「取り込み先」の列と、
各 Sub-issue の文書の `## 取り込み先` の節に「取り込み先: <Epic ブランチ／既定ブランチ>（理由）」として書く。
人は手順7の計画のレビューでこの判断を見て進める（起票前に直せる）。`epic-implement` は書かれた取り込み先に従う。

- **既定は Epic ブランチ**。Sub-issue の PR は Epic ブランチへ入れ、Epic の完了時に Epic の PR で既定ブランチへ取り込む。
- **既定ブランチへ直接入れる例外**は、次の**両方**を満たすときだけ。理由に事情を書く。
  1. **独立に取り込める**（注意事項の2基準の1つ。入れても他を壊さず、半端な状態を残さない）。
  2. **先に出したい・Epic の外で先に必要とされている**などの事情がある。
- **実装の途中で変えたくなったとき**は、ハーネスが変更を提案し、理由とともに Sub-issue に記録してから従う。黙って変えない
  （手順は `epic-implement` の手順4・5）。

**Epic ブランチを作る条件**（計画に書く。起票のとき `epic-create-issues` が従う）:

- 取り込み先が Epic ブランチの Sub-issue が**1つでもあれば作る**。
- **ワークスペース**（計画の置き場が実装先リポジトリの外）で、全 Sub-issue が既定ブランチ向けなら**作らない**
  （計画はワークスペース側にあり、Epic ブランチに載せるものが無い）。この場合は Epic の PR も作らない。
- **単一リポジトリ**で、全 Sub-issue が既定ブランチ向けでも**作る**（計画の置き場として。計画を先に既定ブランチへ入れないため）。

### 7. ユーザーへのレビュー依頼

作成したドキュメントの構成と、**Sub-issue ごとの取り込み先の判断（理由つき）**・Epic ブランチを作るかどうかを報告し、レビューを依頼する。

**注意**: このスキルではコミットしない。`.epic_docs/` のコミットは `epic-create-issues` スキルが行う（`$EPIC_DOCS_ROOT` が実装先リポジトリと同じ場合は Epic ブランチ作成時に、異なる場合はワークスペース側リポジトリ自身の運用に従って別途行う。詳細は `epic-create-issues` の該当手順）。

## 注意事項

- Sub-issue の分割は2基準で判定する。**サイズ（「1 PR で完結する」）はこの2基準を満たした上での
  補助目安**であり、衝突したら2基準を優先する。**2基準は混同しやすいので、それぞれに独立した
  対比例を示す**（「片方は満たすが、もう片方は満たさない」を両方向で）。
  - **独立に検証できるか**（その Sub-issue だけで動作を確認できるか）:
    満たすが「独立に取り込めるか」を満たさない例は、まだ誰も読んでいない設定を追加する場合——単体で
    その設定が期待通り読み込まれることは検証できるが、取り込むと死んだ設定として残る。
  - **独立に取り込めるか**（取り込んでも他を壊さず、死んだ設定・未使用コードのような半端な状態を
    残さないか）: 満たすが「独立に検証できるか」を満たさない例は、既存の呼び出し元を新方式へ一斉に
    書き換える場合——取り込みは安全（他を壊さない）だが、単体では動作を確認できない。
  - どちらか一方でも満たさない候補は、複数の Sub-issue に割らず**1つの Sub-issue にまとめる**。
    Sub-issue（意味のまとまりの単位）と実際に取り込む単位を一致させる判定。2基準の結果は、手順6の
    取り込み先の判断の材料になる（独立に取り込めない候補は既定ブランチへ直接入れる例外の対象にならない。
    入れてよいのは独立に取り込めて、かつ先に出す事情があるものだけ）。
  - 上記2つの対比例とは別種の判定例として、**新設する共有基盤を複数の独立した利用側が使う設計での
    誤判断を防ぐ例**がある: 新設する共有基盤（スキーマ・repository層等）を、互いに独立して動作する
    複数の利用側（エンドポイント・ドメイン等。片方が未対応でも他方の動作に影響しないもの）が使う
    設計では、基盤単体を切り出すのは誤り（「独立に取り込めるか」に違反）——これは上記「どちらか
    一方でも満たさない候補はまとめる」の適用そのものであり、「基盤+最初の利用側」を1つの Sub-issue
    にまとめる。ここで新しく効くのは次の点だけである:
    **残りの利用側はそれぞれ独立した Sub-issue に分けられる**（それ単体で検証・取り込み可能なため）。
    「対称な実装だから一緒に」は2基準のいずれにも根拠を持たない判断であり、残りの利用側をまとめる
    理由にしない。
- 依存関係を明示し、独立に検証・取り込みできるものだけを Phase 内で並行可能と記載する。**並列は
  競合を避けた結果であって目的ではない**——基盤整備のように各段が前段の成果物を要する Epic は
  構造的に直列であり、直列のまま Phase を直列に並べてよい（無理に並行可能と記載しない）。
- コード例は、計画時点で確定できない細部（変数名・ライブラリの正確な API 形状等）まで固めることは
  求めない。ただし上記「実装内容」の観点（型/スキーマ/シグネチャ・分岐条件・接続点）が示す具体度は
  下げてよいという意味ではない——「最終実装と一致しなくてよい」は「具体度を下げてよい」の言い換えではない
- 日本語で記述する（英語のコード例・メッセージはそのまま）
- ブランチ命名は CLAUDE.md のブランチ戦略に従う
- このスキルでは git 操作を行わない（コミットは `epic-create-issues` が担当）
