# harness-help — 今何ができるか・どう使うかを案内する

導入済みのハーネスが**今どんな機能を持っているか**と、**その機能をどう使うか**を1つの入口から案内するスキル。
機能が増えて自分でも把握しきれない、というギャップを埋める。

## 1. 今何が使えるか

導入済みの yosage-dev-harness が提供する skill / agent / rule / hook の一覧は、次節のルーティング表と
このファイルの各節に沿って確認する（個別のパスを覚える必要はない）。

一覧はあくまで「何があるか」の索引。**どう組み合わせて使うか**は次節のルーティング表を見る。

## 2. 「この作業どうやる?」→ 使う skill / flow

やりたいことから、まず着手する skill（複数ある場合は左から順に進む一連の flow）を引く表。

| やりたいこと | 使う skill / flow | ひとこと |
|---|---|---|
| 新規プロダクト/大きな機能の企画を壁打ちでまとめたい | `proposal` | 対話で `.docs/proposal.md` を作る。実装に入ったら凍結 |
| 設計・アーキ判断をしたい（既存コードに沿わせたい） | `grounded-design` → 局所的で複数案・後戻り軽い場合は `deliberate-design`／後戻りが重い・アーキ横断なら `design-doc` | まず内部・外部に接地してから、討議の重さに応じて枝分かれする |
| アーキテクチャを正本化したい | `document-architecture` | `.docs/architecture/` へ書き出す |
| ドメイン用語や命名を揃えたい | `glossary` | ユビキタス言語を一元管理 |
| 単発の変更を進めたい（Epic にするほどでもない） | `issue-create` → `issue-implement` | self-contained な issue を起票してから実装・PR まで進める |
| 大きめの機能を Epic として進めたい | `epic-create-docs` → `epic-create-issues` → `epic-implement` | 計画ドキュメント → Issue/Sub-issue 起票 → 全体実装の順で進む |
| Epic 配下の Sub-issue を1件だけ実装したい | `epic-implement-subissue` | 取り込み先は Sub-issue の本文に従う（既定は epic ブランチ、例外は導入先の既定ブランチ） |
| 複数の worktree を並列で動かしたい | `orchestrate-parallel` | 分配・監視・レビュー・統合をまとめて進行する |
| Epic 向け PR をレビューしたい | `epic-review` | epic ブランチ向け PR を扱う（マージは実行せず人間に促す） |
| 学びを残したい（指摘された・やってみて分かった・設計が決まった） | `capture-learning` | 作業した本人がその場で記録する |
| 過去の判断・落とし穴を引きたい | `recall-knowledge` | 蓄積済みの知識から関連だけ選び出す |
| 溜まった知見をまとめて外へ送りたい | `promote-knowledge` | 明示的に呼んだときだけ動く |
| 使い捨てでコマンドやスクリプトを試したい | `scratch-run` | 使い捨てコンテナで実行し、環境を汚さない |
| 実装とドキュメントがずれていないか揃えたい | `sync-design-docs` | 実装からドキュメントを起こす／既存の記述と突き合わせる |

## 3. 使い方

「この作業どうやる?」と聞かれたら、まず上の表で該当行を探し、そこに書かれた skill/flow を案内する。
複数の skill が矢印でつながっている行は、その順番で進める一連の流れを表す。
表に無い/どれが該当か迷う作業は、1節の一覧で名前や説明を確認してから、近そうな skill を試す。
