# glossary — ユビキタス言語と命名の一元管理

ドメイン用語と「コード上の名前（クラス/モデル/テーブル/フィールド）」の対応を `.docs/glossary.md` に集約し、
**同じ概念は常に同じ名前**で呼ぶ。実装で散らばる命名の揺れを防ぐ。

## なぜ
- 同一概念が `User`/`Account`/`Member` のように散ると、認知負荷・バグ・重複の温床。
- ビジネス側の言葉（ドメイン用語）とコード名を1対1に固定し、設計〜実装〜レビュー〜doc で一貫させる。

## いつ
- **新しいドメイン概念が出たとき**（その場で登録）。
- 命名に迷うとき（既存があれば従う、無ければ登録してから使う）。
- 設計（proposal/yosage-dev-harness:architect）で用語が出たとき、実装で名前を付けるとき、レビューで揺れを見つけたとき。

## `.docs/glossary.md` の形式
```markdown
# 用語集 / ユビキタス言語

| 用語(canonical) | 定義 | コード対応(class / model / table / field) | 使わない別名 |
|---|---|---|---|
| ユーザー / User | サービスを利用する人 | `User` / `users` 表 / `user_id` | Account, Member |
| 注文 / Order   | 確定した購入単位     | `Order` / `orders` 表 / `order_id` | Purchase, Cart |

## 補足（境界が紛らわしい用語）
- <Term>: <他の用語との違い・スコープ>
```
- **canonical を1つに決める**（日本語/英語の対応も書く）。
- コード対応に class・データモデル・テーブル・主要フィールドを書く。
- **使わない別名**を必ず明記（揺れの元を封じる）。

## 運用
- 用語を追加/変更したら表を更新（1概念1行）。捨てた名前は「使わない別名」へ移す。
- 設計・実装・レビューは **この表を正本** として命名する。表に無い概念は**登録してから**使う。
- 参照: `grounded-design`/`yosage-dev-harness:architect`/`yosage-dev-harness:implementer` は命名前に参照。`yosage-dev-harness:consistency-reviewer` は
  「未登録概念」「使わない別名の使用」「同義語の混在」を点検する。

## 原則
- **1概念1名**: 同じ概念を別名で呼ばない。
- **ビジネス言語に合わせる**: コード名はドメイン用語に対応させる。
- **正本は glossary**: 迷ったら表に従う。無ければ登録してから使う。
