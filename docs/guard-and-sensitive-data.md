# ガードと機密

このプラグインは、Claude が実行する操作のうち危険なものを、実行の**前**に止める（ガード）。
また、秘密・個人情報・組織の識別子が、リポジトリや GitHub に残らないよう、種類ごとに別の
手当てをしている。

## ガードの基本

- ガードは、プラグインが有効なリポジトリのすべてのセッションで動く。
- 止めるのは**Claude の操作だけ**。人がエディタや別のターミナルで行う操作（コミットを含む）は
  範囲外で、ガードには見えない。
- **解除の手段は無い**。環境変数などで切る方法を用意していない。
- 止まると、Claude は理由を受け取り、**報告して止まる**。本当に必要な操作なら、**人が自分の
  ターミナルで行う**。

## 何が止まるか

次は、実際に止まるものの主な例で、**網羅ではない**。表に無い操作が止まることもある（表に無いから
ガードではない、とは判断しない）。

| 種類 | 止まるもの |
|---|---|
| 破壊的なコマンド | ルートやホーム配下の再帰削除、ディスクデバイスへの直接書き込み、`chmod 777`、fork bomb、`~/.ssh/authorized_keys` への書き込み |
| ダウンロードの直接実行 | ダウンロードした内容をそのままシェルに渡す実行（`curl ... \| sh` など） |
| 履歴の書き換え | `git push` の force（`--force`・`-f`・`--force-with-lease`・`+` 付きの指定）。ブランチを問わず止まる |
| 変更の破棄 | `git checkout -- <path>` や `git checkout .`（未コミットの変更を失う）。ブランチの切り替えや `-b` は止まらない |
| マージ | PR のマージ操作（`gh pr merge`、`gh api` 経由のマージ）。**マージは人だけが行う** |
| 保護ブランチへのコミット | `main`・`master`へ直接 `git commit` すること。GitHub の既定ブランチも対象だが、`origin/HEAD` が引けるときだけ（引けない clone では `main`・`master` だけ。`git remote set-head origin --auto` で引ける） |
| コミット時の取りこぼし | `git commit -a`、パス指定つきのコミット（ステージ前の内容の検査をすり抜けうる）。`git add` で明示してからコミットする |
| 一括ステージ | 300ファイルを超える内容をステージしたままのコミット |
| 秘密の混入 | ステージした内容に秘密の形式（下記）が見つかったとき。`gh pr` / `gh issue` の `create`・`edit` の本文に秘密が入っているとき（コメントやレビューの本文は、秘密の検査の対象外） |
| 秘密ファイルの読み取り | `.env` と変種、`*.pem`、`*.key`、`id_rsa`、`secrets/` 配下を、Read・Grep・Bash の `cat` `grep` `head` `tail` `less` `find` で読むこと。`.env` 系の `*.example` `*.sample` `*.template`（テンプレート）は対象外（`secrets/` 配下は接尾辞に関係なく対象） |
| 作業ツリーの外 | 隔離された作業ツリーで動く実装役が、割り当てられた作業ツリーの外へ書き込む・git 操作をすること。作業ディレクトリが `.claude/worktrees/<id>` の下にあるときだけ効く（それ以外のセッションでは働かない） |
| PR や issue の本文 | `../` のような、リポジトリの外を指すパスを書くこと（GitHub 上で壊れるため） |
| 環境を汚す操作 | `pip install` などのグローバルなインストール（`brew install`・`cargo install`・`npm -g` なども）。`/tmp` に置いたスクリプトを直接実行すること。`compose.yml` があるリポジトリで、アプリのランタイムをホストで直接動かすこと |

ガードは「最後の安全網」で、粗い一致で止める。そのため、**まれに本来は問題ない操作を止める**
ことも、巧妙に書かれた操作を見逃すこともある。特に秘密ファイルの Bash 経由の読み取りは、
`cat` などの直接の呼び出しだけを狙う網で、コピーやリダイレクト経由までは塞がない。

## 止まったとき

1. Claude の報告（どのガードで、何が理由か）を読む。
2. 次のどれかで対応する。
   - **進め方を変えれば足りる場合**（例: 保護ブランチへのコミット → 作業ブランチを切る、
     `git commit -a` → `git add` してからコミット、`/tmp` のスクリプト → `.claude/tmp/` に
     置くか使い捨てコンテナ経由で実行）。Claude に指示し直す。
   - **本当に必要な操作の場合**（force push・マージ・秘密ファイルの読み取りなど）。**人が自分の
     ターミナルで行う**。
3. 頻繁に同じ止まり方をする場合は、[よくある詰まり](troubleshooting.md) を見る。

マージは、許可プロンプトで承認しても代わりにならない。ハーネスの Bash からはマージを実行でき
ない。

## 秘密・個人情報・組織の識別子

この3つは性質が違うため、検出と手当てが別になっている。

| 種類 | 例 | 検出 | 手当て |
|---|---|---|---|
| 秘密 | API キー・トークン・秘密鍵 | 形式が決まっているので機械的に検出 | **ブロック**（コミット前・PR/issue 本文の投稿前） |
| 個人情報 | 氏名・住所など | 自由な記述なので機械では判定できない | Claude の目視と、レビュー役の指摘 |
| 組織の識別子 | 自組織の名前・リポジトリ名・社内ツール名 | 宛先によって正当にも不適切にもなるので、単一の禁止パターンにできない | **警告のみ**（レビューの投稿直前） |

### 秘密

- 検出するのは、次の形式の**既知のトークン**: GitHub の PAT、AWS のアクセスキー ID、Slack の
  トークン、Google の API キー、OpenAI の API キー、Stripe のキー、PEM 形式の秘密鍵。それ以外の
  形式の秘密（独自のパスワードなど）は、機械的には見つからない。
- **置き場**: 運用で要る秘密の値（例: 通知の webhook URL）は、git で追跡しない
  `.claude/yosage-dev-harness.local.json` に置く。コミットや issue・PR の本文に書かない。
- **コミット前**: Claude は `git commit` の前に、ステージした差分を秘密と個人情報の観点で
  見直す。ガードも、コミット時にステージした内容を実際に読んで検査する。ワークスペースでは
  同居する子リポジトリへのコミットも対象になる（[ワークスペース](workspace.md)）。
- **見つかったとき**: コミットせず、定位置（上記のファイル）へ退避するか、値を取り除く。判断に
  迷うときは、黙って通さず人に確認する。
- **リポジトリ側の保険**: ガードが見えるのは、このプラグイン経由の Claude の操作だけ。
  GitHub の **push 保護**（secret scanning の push protection）も併用すると、経由を問わず
  秘密の push を止められる。人が行うコミットには gitleaks などの検査を自分で用意する。
- **読み取りの遮断**: 秘密ファイルの読み取りは、上の表のとおりガードが止める。加えて、推奨設定の
  見本 `.claude/yosage-dev-harness.recommended-settings.json`（`/yosage-dev-harness:setup` が作る）に、
  Read の拒否の設定がある。Claude Code はこのファイルを読まないので、使うなら自分の
  `.claude/settings.json` へ移す（[README の導入先に書かれるもの](../README.md#導入先に書かれるもの)）。

### 個人情報

機械的な検出はない。Claude は差分を読んで判断し、必要性を確かめたうえで、取り除くか、追跡
されない場所へ退避する。レビュー役（`yosage-dev-harness:code-reviewer`）も安全網になる。

### 組織の識別子

秘密と違い、同じ語が自分の宛先では正当で、他の組織の宛先では不適切になる。そのため禁止語の
リストは持たず、**投稿先**と、ワークスペースに同居するリポジトリの owner と repo 名を、
git の remote から調べて照らす。

- 警告が出るのは、**投稿先の owner が自組織（最も外側の git リポジトリの owner）と異なるとき**で、
  `yosage-dev-harness-gh-review` 経由のレビュー・返信の本文を照らすときだけ。自組織への投稿では
  出ず、PR や issue の作成・コメントの本文も照らさない。
- 他組織の宛先への投稿で、本文にワークスペース内の別リポジトリの識別子が含まれていそうなら、
  投稿の直前に**警告**する。止めはしない。
- 警告には、一致した語そのものは出さず、宛先と件数だけを出す（出力が別の場所に転記されるのを
  避けるため）。

他社のリポジトリで作業するときは、導入の単位を**ローカル単位**にして、自社の非公開リポジトリ名が
その相手のリポジトリに残らないようにする（[README のセットアップ](../README.md#セットアップ)）。

### 検査を頼むときの書き方

「この値が混ざっていないか確認して」と、確認したい**値そのもの**を指示に書くと、受けた側が
その値を報告に書き写して、そのまま投稿してしまう。確認の指示は、性質や分類で書く。

- 悪い例: 「この秘密（`<実際の値>`）が混ざっていないか確認して」
- 良い例: 「秘密が混ざっていないか確認して」

「該当なし」という報告にも、対象の値を書かせない。

## ガード以外に自動で動くもの

| 動くもの | 内容 |
|---|---|
| 整形 | 編集したファイルを、言語に応じて自動整形する（失敗してもセッションは止まらない） |
| 接地の確認 | 設計ドキュメントの `path:line` の引用が実在するかを確かめ、無ければ Claude に自己修正を促す |
| 知見の書式検査 | 知見のファイルを書いたとき、書式を検査して知らせる |
| コミットの署名の確認 | コミットの `Co-Authored-By` 署名が、リポジトリの方針に合っているか気づかせる（止めはしない） |
| 通知 | 設定した webhook（Slack か Discord）に通知を送る。`notify.url` を設定したときだけ動く |
| 知識ストアの同期 | セッション開始時に、有効なら共有ストアを取り込む（[知見](knowledge.md)） |
| 前提の確認 | セッション開始時に、`jq` か `python3` が使えるかなどの前提を確かめ、問題があれば知らせる |

通知は、既定では無音。設定項目は [README の設定](../README.md#設定) を見る。
