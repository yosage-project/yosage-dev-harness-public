# 知見

作業の前に過去の判断を引き（recall）、作業のあとに学びを残す（capture）。この繰り返しで、
同じ間違いを繰り返さず、プロジェクトが少しずつ賢くなる。

- **recall（前）**: 着手前に、今の作業に関係する過去の判断・落とし穴だけを選んで読む。
- **capture（後）**: 指摘された・やってみて分かった・設計を決めた、というときに学びを残す。

どちらも、**作業をした本人**が行う。実装役が実装したなら実装役が、メインが設計や統制を
したならメインが行う。人が毎回頼む必要はない。この規律は常に Claude に渡されている
（ルール `knowledge`）。

## 2種類の知見

| 種類 | 置き場 | 範囲 |
|---|---|---|
| ローカル | リポジトリの `.claude/knowledge/<ドメイン>/` | そのプロジェクトだけ |
| グローバル | 共有ストア（独立したリポジトリ）。各プロジェクトには読み取り専用の写しが届く | 組織やチームの全プロジェクト |

見分ける問いは「**この学びは、他のプロジェクトでも成り立つか**」。成り立たないならローカルに、
成り立つならグローバルの候補にする。

## ローカルの知見

1件につき1ファイル、`.claude/knowledge/<ドメイン>/YYYY-MM-DD-<スラッグ>.md` に書く。1件に1つの
ルールと、その理由を書く。雛形は `yosage-dev-harness-knowledge-template` の出力で、
先頭の項目（frontmatter）に `date` / `domain` / `tags` / `scope` / `status` / `summary` を持つ。

- `scope`: `local`（そのプロジェクト固有）または `global`（全プロジェクト共通の候補）。
- `status`: `active`（有効）/ `superseded`（新しいものに置き換えた）/ `archived`（後継なしで退役）。
  置き換わった知見も、判断の履歴として**消さずに残す**。
- 外部の資料（言語の定石・公式ドキュメント等）に基づく知見は `source:`（URL）と `checked:`
  （確認した日）を持つ。

ローカルの知見は、既定ではコミット対象になり、チームで共有できる（`.claude/` ごと無視している
リポジトリでは当てはまらない）。索引ファイルは作らない。一覧は
次のコマンドで取り出す（`<ドメイン>` は省略可）。

```bash
yosage-dev-harness-knowledge-index .claude/knowledge --list <ドメイン>
```

知見のファイルを書くと、書式の検査が自動で走り、壊れた項目があれば知らせる。

### 繰り返し効くものは、常に効く形へ

何度も効く判断は、生の知見のままにせず、常時適用される場所に移す。

- レビューの判断基準 → `.claude/yosage-dev-harness-review-criteria.md`
- 特定のパスに対するコーディングやテストの規約 → `.claude/rules/<該当パス>/coding.md`（または `testing.md`）
- アーキテクチャの判断と設計意図 → `.docs/architecture/`

## recall: 作業前に引く

実装役などが着手前に自動で行う。人が明示的に引きたいときは次を使う。

```
/yosage-dev-harness:recall-knowledge
```

既定では、司書役のサブエージェント `yosage-dev-harness:librarian` に「ドメイン」と「何を判断したいか」を
渡す。司書役は膨大な知見を作業側の文脈に載せず、**関係するものだけを要約**して返す。各項目には、
今も成り立つかの判定が付く。

| 印 | 意味 |
|---|---|
| `✓接地確認` | 根拠がまだ実在し、教訓が成り立っている |
| `⚠要確認` | 根拠が動いた・ずれた疑いがある |
| `✗陳腐化` | 根拠が消えた、または教訓が成り立たなくなった |
| `∅接地対象なし` | 根拠を持たない規範的な判断で、確かめる手段が無い |
| `⇧昇格候補` | 他のプロジェクトでも効きそう。グローバルへの昇格を検討できる |
| `⇧staging未PR` | グローバル候補として印は付いたが、まだ共有ストアに出していない |

`⚠` や `✗` が付いた知見は、作業側がその場で直す（新しい知見で置き換える、または退役させる）。
大きな直しは、follow-up の issue にして作業を続ける。

外部の定石を調べ直す必要があるときは、調査役 `yosage-dev-harness:researcher` が出典つきで調べる。
ただし、モデルがもともと知っている一般論は引かない・残さない。

## capture: 作業後に残す

次のようなときに、作業した本人が残す。

- 人に指摘・訂正された。
- レビューで同種の指摘が繰り返された。
- 実装中に「やってみて分かった」制約や事実が出た。
- 設計を決めた。
- タスクの振り返り。

残すのは、そのプロジェクトやモデルがもともと持っている知識との**差分**だけ。「継承より合成」
のような一般論は残さない。書き込む前に、1件1ルールになっているか、固有の事実と一般形が
混ざっていないか、`scope` が合っているかを見直す。

手動でも呼べる。

```
/yosage-dev-harness:capture-learning
```

## 共有ストアを設定する（グローバルの知見）

グローバルの知見は、**共有ストア**という独立したリポジトリで管理する。プロジェクトから直接は
書かない。各プロジェクトは、セッション開始時にストアの写しを受け取るだけ。

### 雛形から始める

ストアは、**公開のテンプレートリポジトリ `yosage-dev-knowledge-template`** から作るのが早い。
ハーネスの公開リポジトリと並んで公開され、GitHub の「Use this template」で自分の組織のリポジトリ
として作れる。中身は、下の「ストアの形」に沿った最小の一式(README・LICENSE・役割の説明だけの
`review/criteria.md`・空の `knowledge/`)。見本のエントリは置かない(消し忘れが同期で全プロジェクトに
配られ、本物の知見として引かれるため)。作ったら、README を自分の組織の運用に合わせて書き換える。
エントリは最初の昇格 PR で入る。

ストアのリポジトリ名は、組織ごとに自由に付けてよい(例: `<組織名>-knowledge`)。雛形の名前に
合わせる必要はない。ハーネスはリポジトリの名前を見ない(取得は `knowledge.source` の URL と `knowledge.ref` で行い、
中身は下の「ストアの形」に従う)。

雛形の元はハーネスの `templates/knowledge-store/` にあり、ハーネスのリリースのたびに公開側へ写される
(雛形の README の「合わせたハーネスの版」が、どの版の形に合わせたかを示す)。

手で作るなら、次の「ストアの形」を満たす空のリポジトリを用意すればよい。

### ストアの形

ストアの形の約束は、この節が人が読む正本。機械が判定する側の正本は、形の検査コマンド
(後述の「ストアの形を確かめる」)。

#### ディレクトリの形と、置いてよいファイル

```
<ストアのルート>/
├── README.md                      # ストアの運用の説明(必須)
├── LICENSE                        # 使ってよい条件(置くことを勧める。検査はしない)
├── review/
│   └── criteria.md                # 組織が足していくレビュー観点(必須)
└── knowledge/
    └── <ドメイン>/
        └── YYYY-MM-DD-<スラッグ>.md   # 知識のエントリ
```

| 場所 | 置いてよいもの |
|---|---|
| ルート直下 | `README.md`・`LICENSE`・`.gitignore`・`.gitattributes`、ディレクトリ `knowledge/`・`review/`(ほかに、git の管理用の `.git`・`.github`、手元のハーネス導入の `.claude`)。それ以外は置かない |
| `review/` | `criteria.md` だけ(同期が読むのはこれだけ) |
| `knowledge/` の直下 | ドメインのディレクトリだけ。**索引(`INDEX.md`)は置かない** — 索引は各プロジェクトが同期のときにエントリの項目から生成する。ファイルを足すだけの PR が衝突しないための決まり |
| `knowledge/<ドメイン>/` | エントリ `*.md` だけ(`_` で始まる `.md` は、雛形などの置き場として読み飛ばされる) |

空のディレクトリを git に残すための `.gitkeep` は、`knowledge/`・`knowledge/<ドメイン>/`・`review/` のどこにあってもよい。

同期が読むのは `knowledge/` と `review/criteria.md` だけ。README や LICENSE は、ストアに置かれる
だけで各プロジェクトへは届かない。

- **ドメイン**のディレクトリ名は、小文字の英数字とハイフン(例 `api`・`process`)。数に決まりはなく、
  必要になったときに作る。`global` は予約名(各プロジェクトの同期先 `knowledge/global/` と衝突する)で使えない。
- **ファイル名**は `YYYY-MM-DD-<スラッグ>.md`。日付はエントリの `date` と同じ、スラッグは小文字の
  英数字とハイフン(英語の kebab-case)。

#### エントリの項目(先頭の frontmatter)

エントリの先頭には `---` で囲んだ項目を書く。書き出し用の雛形は `yosage-dev-harness-knowledge-template`
が出力する。1項目は1行の `名前: 値` で書く(値を複数行にしない)。

| 項目 | 必須か | 意味と値 |
|---|---|---|
| `date` | 必須 | 記録した日。実在する `YYYY-MM-DD`。ファイル名の日付と同じ |
| `domain` | 必須 | ドメイン。置かれたディレクトリ名と同じ |
| `tags` | 必須 | 検索用のタグ。`[a, b]` の形(無ければ `[]`) |
| `scope` | 必須 | ストアのエントリは `global`(`local` のものはストアに置かない) |
| `status` | 必須 | `active`(有効)・`superseded`(新しいものに置き換えた)・`archived`(後継なしで退役)。古くなったものも消さず、この値で残す |
| `summary` | 必須 | 一覧に出る1行の要約。**1行のプレーンスカラー**で書く(行頭に `>` や縦線を置かない・複数行にしない・空にしない) |
| `id` | 任意 | エントリの識別子。省略するとファイル名のスラッグが識別子になる。ファイル名を変えても参照が壊れないよう、明示を勧める |
| `supersedes` | 任意 | 置き換えた古いエントリの `id` |
| `archived` | 任意(`status: archived` のとき必須) | 退役した日。`YYYY-MM-DD` |
| `source` | 任意 | 外部の資料(言語の定石・公式ドキュメント等)に基づくときの出典 URL |
| `checked` | `source` があるとき必須 | 出典を最後に確認した日。`YYYY-MM-DD` |

**値の後ろに `# …` のコメントを書かない。** 索引と同期は行末までを値として読む(YAML の行末コメントは
解釈されない)ので、たとえば `status: archived   # 退役` は `archived` と読まれない。
`yosage-dev-harness-knowledge-template` の出力は各項目に説明のコメントが付いているので、埋めたら消す
(`summary` だけは本文に `#` を含んでよい)。

`id` は、明示したものもファイル名から導かれるものも、ストアの中で一意にする。`supersedes` は、
ストアの中のエントリの `id` を指す(カンマ区切りで複数可)。

上にない項目を足しても検査は落ちない。本文は、1件に1つのルールと、その理由を書く(雛形の見出しは
「判断 / ルール」「なぜ」「根拠 / 実例」「適用」)。エントリは、ほかのリポジトリを開かなくても意味が通る
形にする。issue や PR の番号・非公開のリポジトリ名・社内ツールの名前は書かない
(構造監査が番号の残留を検出する)。

#### `review/criteria.md` の役割

レビューのしかたと基本の観点は、ハーネスのレビュアーの定義が持つ。ストアの `review/criteria.md` は、
**組織が経験から足していくレビュー観点だけ**を置く。最初はほぼ空でよく、**ファイルは置いておく**
(同期は「ストアにあれば上書き」なので、ファイルが無くなっても各プロジェクトの写しは消えないが、
無いストアは形の検査が落ちる)。

#### ストアの README に書いておくこと

README はストアの運用の説明で、同期では読まれない。形の約束はここ(この文書)が持つので、README には
書き写さずリンクする。少なくとも次を書く。

- ストアの役割と、知識の足し方(各プロジェクトから `promote-knowledge` で昇格の PR を出す)。
- **昇格の PR を向けるブランチと、マージのしかた**。`promote-knowledge` は、PR を向けるブランチを設定
  `knowledge.ref` から、マージ方式をストアの README の規約から読んで従う。既定は「ブランチ `main` に PR、
  マージはマージコミット」。
- 昇格の PR は**人がレビューしてからマージする**こと。
- 越えない線(客先や他社の知識を集めない、案件固有の判断を入れない、自動で全体に効かせない等)。

#### 形は基本的に壊さない

形はハーネスと各ストアが共有する約束で、基本的に壊さない。形が原因の不具合はこれまで出ていないため、
ストアに形の版を宣言して照合する仕組みは持たない。**形を壊す変更が必要になったら、その変更の一部として、
ストアへの版の宣言(宣言が無いストアは版1とみなす)と、移行の手段を入れる。**

#### ストアの形を確かめる

形の検査コマンドで、ストアの形を確かめられる。自分のストアを作ったあと、または PR を出す前に使う。
ストアのルートを渡す(読むだけで、ストアには何も書かない)。

```bash
yosage-dev-harness-knowledge-store-check <ストアのディレクトリ>
```

違反があれば、1行1件(`<ストアからの相対パス>`・検査コード・メッセージをタブで区切る)を標準出力へ出して
終了コード 1 で終わる。違反が無ければ何も出さず 0 で終わる(終了コード 2 は使い方の誤り、または検査できなかったとき)。
見るのは、上の「ディレクトリの形と、置いてよいファイル」「エントリの項目」「`review/criteria.md` の有無」と、
エントリが索引に載ること、`id` が重複していないこと、`supersedes` の指す先がストアにあること、
issue や PR の番号が残っていないこと。**見ないもの**: エントリ本文の `[[id]]` リンクが解決できるか、
本文のファイルパスの参照が実在するか、導入先のパス表記が残っていないか(これらは各プロジェクトの
構造監査の領域で、ストア単体では解決先が決まらない)。

`python3` が要る。無ければ「検査できない」として終了コード 2 で終わる(何も検査せずに合格にはしない)。
索引や構造監査の部品が想定外に失敗したときも同じく 2 で、原因を標準エラー出力へ出す。ストアの CI から
呼んでもよい。

### 設定

ストアを使うのは**任意**（既定は無効）。使う場合は、プロジェクトの
`.claude/yosage-dev-harness.local.json`（git で追跡しない）に、既定から変える項目だけを書く。

```json
{
  "knowledge": {
    "enabled": true,
    "source": "<共有ストアのリポジトリ URL>",
    "ref": "main"
  }
}
```

| 項目 | 説明 |
|---|---|
| `knowledge.enabled` | `true` で同期を有効にする。既定は `false` |
| `knowledge.source` | ストアのリポジトリ。`git clone` できる URL |
| `knowledge.ref` | 取得するブランチかタグ。既定は `main` |

設定項目の全体は [README の設定](../README.md#設定)。

### 同期の挙動

- セッション開始時に、背景で取得する。セッションの開始は待たされない。
- 届く先は、`.claude/knowledge/global/`（知見）と `.claude/review/criteria.md`（判断基準）。
  どちらも git で追跡されず、**読み取り専用の写し**として扱う。手で直しても、次の同期で
  置き換わる。ストアを直すときは、次の「昇格」を使う。
- 無効のとき、取得できないとき（オフライン・権限・URL の誤り）は、何もせずセッションを続ける。
  取得できなかった場合は、前回の写しがそのまま使われる。
- 取得の記録は `.claude/knowledge/.sync-log`、写しが反映したストアの版は
  `.claude/knowledge/.global-sync` にある。

## 昇格: ローカルの知見をストアへ出す

グローバルの価値があると判断した知見は、次の2段階で共有ストアへ出す。

1. **印を付ける（capture のときに行う）**: 知見の `scope` を `global` にして、ローカルに置いたまま
   にする（staging）。判断基準なら `.claude/review/criteria.global-proposed.md` に書く。この時点では
   ストアへ送らない。
2. **ストアへ出す（人が明示的に起動する）**:

   ```
   /yosage-dev-harness:promote-knowledge
   ```

   このスキルは**自動では動かない**。ある程度たまったら人が打つ。たまった候補が0件なら、その旨を
   報告して何もしない。ストアの設定（`knowledge.enabled` と `knowledge.source`）が無ければ、
   設定を求めて止まる。

`promote-knowledge` は、候補を次のように扱う。

1. 候補を集める。ワークスペースでは、自分のリポジトリと各メンバーリポジトリの候補をまとめる
   （[ワークスペース](workspace.md)）。
2. 候補を、確認することの種類ごとに分ける（外部の要件由来・ライブラリの挙動由来・手法の記録・
   実装上の落とし穴）。
3. 本当に全プロジェクトで成り立つか、案件固有の判断が混ざっていないかを確かめる。混ざって
   いれば一般部分だけを出す。成り立たないなら昇格せず、`scope` を `local` に戻して理由を書く。
4. 特定のリポジトリや組織に依存する参照（issue や PR の番号・リポジトリ名・社内ツール名など）を
   取り除き、ほかのプロジェクトで読んでも意味が通る形に書き直す。
5. `source:` を持つ候補は、出典を実際に開いて、書かれた内容が原典にあるか照合する。原典と
   矛盾するときは、昇格を止めて人に差し戻す。原典に無い主張のとき、出典を開けず照合できない
   ときも昇格しない。
6. ストアを一時的に clone してブランチを切り、重複を確かめてから PR を出す。

**人がやること: ストアの PR をレビューしてマージする。** これが唯一の関門で、自動ではマージ
されない。マージされたら、`promote-knowledge` は、ローカルの昇格元の知見を削除する（昇格は
コピーではなく移動。1つの事実の置き場は1つにする）。そのプロジェクト固有の使い方に価値が
残るなら、それは別の `scope: local` の知見として書き直して残す。

昇格を忘れても何も壊れない（共有が遅れるだけ）。

## 困ったとき

知見が引けない・ストアが同期されない、というときは [よくある詰まり](troubleshooting.md)。
