# はじめての1件

小さな修正を1件頼み、PR がマージされるまでを通して説明する。例として「README の誤字を直す」を
頼む場面で考える。

導入が済んでいること（[README のセットアップ](../README.md#セットアップ)）と、対象リポジトリに
GitHub の `origin` があること、`gh`（GitHub CLI）でログイン済みであることが前提。

## 1. 頼む

普通の言葉で頼んでよい。

```
README の「セットアップ」の手順2にある誤字を直して。
```

プラグインが有効なセッションでは、変更の規模を分ける決まり（ルール `change-lanes`）が
常に Claude に渡されている。Claude はまず、頼まれた変更がどの進め方に当たるかを判定する。
誤字の修正は「自明な小修正」なので、issue は必須ではない。

追跡が要る変更（あとで引き継ぐ・セッションをまたぐ）にしたいときは、issue を作ってから実装を頼む。

```
/yosage-dev-harness:issue-create 誤字を直す
/yosage-dev-harness:issue-implement <owner>/<repo>#<N>
```

単一のリポジトリでは、`<N>`（issue 番号）だけでもよい。複数リポジトリのワークスペースでは
`<owner>/<repo>#<N>` の形が必須（[ワークスペース](workspace.md)）。

## 2. 実装は実装役が隔離した場所で行う

Claude 本体（メインのセッション）は実装せず、実装役のサブエージェント
`yosage-dev-harness:implementer` に任せる。自明な小修正でも同じ。メインは分配・監視・判断を担う。

実装役は次の順で進める。

1. 割り当てられた作業ツリー（git worktree。`.claude/worktrees/<id>` の下）の中で作業する。
   作業ツリーを用意するのは、実装役を呼び出す側（Claude 本体）。実装役は着手時に、自分の
   作業ディレクトリがその配下かを確かめ、違えば（共有のチェックアウトにいれば）何も変更せず、
   報告して止まる。共有のチェックアウトは触らない。
2. 着手前に、そのドメインの過去の判断・落とし穴を知見から引く（[知見](knowledge.md)）。
3. 導入先の既定ブランチから `<type>/<name>` のブランチを切る（例: `docs/readme-typo`）。
   `<type>` は `feat` / `fix` / `refactor` / `chore` / `docs` / `test` / `perf` のどれか。
4. 実装し、テストなどの検証を走らせる。
5. コミットする。メッセージは `<type>(<scope>): <要約>` の形で、issue があれば末尾に
   `Closes #<N>` を付ける。
6. push して **draft PR**（下書きの PR）を作る。

実装の前に、issue に「未解決の問い」（`Open Questions`）が書かれていれば、Claude は実装を
始める前に整理する。実装する物自体が変わる問いは、**人に選択肢を示して答えを求める**。実装中に
確かめれば足りる問いは、仮定として記録して先へ進み、まとめて知らせる。

## 3. 一次レビュー

draft PR ができると、Claude はレビュー役のサブエージェント `yosage-dev-harness:code-reviewer` に
差分を見せる（正しさ・設計・テスト・セキュリティの観点）。指摘は PR の該当行にコメントとして
付く。

- 欠陥は実装役が直し、対応したスレッドを resolve する。
- 設計上の好みや範囲の判断にかかわる指摘は、直す前にメインが裁定する。前例が無ければ**人に聞く**。
- 範囲外の指摘は issue にして残す。

自明な小修正に限り、一次レビューは Claude 自身の見直しで代えてよい。それ以外の進め方では、
`code-reviewer` によるレビューが必須（[変更の規模ごとの流れ](workflows.md)）。

## 4. ready にして、人がマージする

指摘への対応が済むと、Claude は PR を draft から ready に変えて、PR の URL を知らせる。
これは「人のレビューをお願いします」の合図。

**ここが人の仕事: PR を読んで、自分の手でマージする。**

- Claude はマージを実行できない（ガードが止める。[ガードと機密](guard-and-sensitive-data.md)）。
  許可プロンプトで承認しても代わりにはならない。
- マージは**マージコミット**で行う（squash も rebase もしない）。
- PR 本文は、最後の状態に合わせて更新されている。本文と差分が食い違っていないかも見る。

## 5. マージのあと

マージを確認すると、Claude は次の作業に入る前に、その作業が作ったブランチと作業ツリーを
掃除する。先に手元の base ブランチを `yosage-dev-harness-update-base` で origin に追いつかせる。
早送りできないとき・未コミットの変更があるときは進めずに、その理由を人に知らせる（掃除は続ける）。
消すときは、未マージのブランチや未コミットの変更が残っていれば失敗するコマンドを
使う。消せなかったものは残して、どうするかを人に尋ねる。

また、作業の中で分かったこと（指摘された・やってみて判明した・設計を決めた）は、実装役が
知見として残す。次回以降の作業の前に引かれる（[知見](knowledge.md)）。

## 流れの全体

```
人: 頼む
 └→ Claude: 規模を判定（必要なら人に問いを確認）
     └→ 実装役: 隔離した作業ツリーで実装 → 検証 → コミット → draft PR
         └→ レビュー役: 一次レビュー → 実装役が対応
             └→ Claude: ready にして URL を知らせる
                 └→ 人: PR を読んでマージ
                     └→ Claude: ブランチと作業ツリーの掃除・知見の記録
```
