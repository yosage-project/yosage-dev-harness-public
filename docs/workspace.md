# ワークスペース

複数のリポジトリを1つの案件として扱う構成のこと。例えば、あるディレクトリの直下に、
バックエンドとフロントエンドなど複数のリポジトリが並び、そのディレクトリ自体も
（計画や横断の文書を置くための）リポジトリになっている、という形。

このページは、1つのリポジトリだけで使うなら読まなくてよい。

## 設定する

設定ファイルの `workspace` を `true` にする。`/yosage-dev-harness:setup` は、ワークスペースの
直下で実行すると、設定ファイルにまだ `workspace` のキーが無く、直下に git リポジトリ
（`.git` を持つ子ディレクトリ）が2つ以上あるとき
`workspace: true` にするかを提案する。

```
/yosage-dev-harness:setup
```

後から変えるときは、`.claude/yosage-dev-harness.local.json` の `workspace` を直接書き換える。
`/yosage-dev-harness:update` は `workspace` を書き換えない。設定項目は [README の設定](../README.md#設定)。

`workspace: true` にすると、次の挙動が変わる。

| 場面 | 挙動 |
|---|---|
| issue の指定 | 番号だけの指定（`<N>`）を受け付けず、`<owner>/<repo>#<N>` の形を求める |
| 知見の引き出し | 自分のリポジトリと共有ストアに加えて、各メンバーリポジトリの知見も引く |
| 知見の昇格 | 昇格候補を、自分と各メンバーリポジトリからまとめて集める |

## issue の指定は `<owner>/<repo>#<N>`

ワークスペースの直下は、それ自体がリポジトリであることが多い。番号だけを渡すと、本来の
メンバーリポジトリではなく、ワークスペース側のリポジトリの同じ番号の issue を取り違える恐れが
ある。これを避けるため、ワークスペースでは番号だけの指定を受け付けず、止まって
`<owner>/<repo>#<N>` の形での指定を求める。

```
/yosage-dev-harness:issue-implement <owner>/<repo>#<N>
/yosage-dev-harness:epic-implement <owner>/<repo>#<N>
/yosage-dev-harness:epic-review <owner>/<repo>#<N>
```

## Epic を複数リポジトリで進める

Epic の流れ（[Epic の進め方](epic.md)）は同じで、次の点が違う。

- **計画ドキュメントの置き場**: `.epic_docs/` は、実装先のメンバーリポジトリの中ではなく、
  「作業ディレクトリから上へたどって見つかる、最も外側の git リポジトリ」の直下（ワークスペース側）に
  置かれる。計画はワークスペース側のリポジトリ自身の運用でコミットする。
- **Epic の issue と Sub-issue**: 実装先のメンバーリポジトリに立てる。起票のとき、対象リポジトリを
  `<owner>/<repo>` で確認される。
- **Epic ブランチと Epic の PR**: 実装先のメンバーリポジトリに作る。取り込み先が Epic ブランチの
  Sub-issue が1つもない（全件が既定ブランチ向け）ときは、Epic ブランチも Epic の PR も作らない。
  Sub-issue の PR は、最初のものが Epic ブランチに取り込まれた時点で、draft の Epic の PR が作られる。
- **実装役の作業ツリー**: 実装先が作業ディレクトリのリポジトリと別のリポジトリのとき、実装役の
  隔離（`isolation: worktree`）は使えない（その作業ツリーから実装先に届かないため）。代わりに
  メインが、実装先のリポジトリの `.claude/worktrees/<id>` の下に作業ツリーを作り、その絶対パスを
  実装役に渡す。置き場がここから外れると、作業ツリーの外への書き込みを止めるガードも、完了後の掃除も
  働かない。
- **完了時の計画**: ワークスペースでは、実装との差分（変えた判断・やらなかったこと）を計画に
  追記してあることが、Epic の完了の条件になる。

## 知見をまたぐ

ワークスペースのセッションと、メンバーリポジトリの中のセッションで、引く範囲が違う。

| 起動した場所 | 引く範囲 |
|---|---|
| ワークスペースの直下 | 自分の知見・共有ストア・各メンバーリポジトリの知見 |
| メンバーリポジトリの中 | そのリポジトリの知見・共有ストアだけ（上位や兄弟のリポジトリは見ない） |

昇格（`/yosage-dev-harness:promote-knowledge`）は、ワークスペースの直下で行うと、各メンバー
リポジトリの候補をまとめて扱う。昇格のあと、ローカルの元の知見を消す変更は、それぞれの
メンバーリポジトリの中で、通常の PR の流れ（draft → レビュー → ready → 人がマージ）に乗せる。
詳しくは [知見](knowledge.md)。

## profile はワークスペース側に書く

導入先固有の座標（スタック・検証コマンド・リポジトリごとの扱い）は
`.claude/rules/<名前>/profile.md` に書く。`/yosage-dev-harness:document-profile` で
下書きを作るとき、調べる対象はメンバーリポジトリでも、**書き出し先は常にワークスペース側**になる。
書式と所有の考え方は [README の profile](../README.md#profile導入先固有の座標)。

## 導入の単位と他社のリポジトリ

メンバーに他社のリポジトリが含まれるときは、導入の単位を**ローカル単位**（`--scope local`）にする。
プロジェクト単位だと、相手のリポジトリの `.claude/settings.json` に、自社の非公開リポジトリ名（＝
マーケットプレイスの場所）が書かれてコミットされてしまう
（[README のセットアップ](../README.md#セットアップ)）。

コミット時の秘密の検査は、ワークスペースの下の子リポジトリへのコミットにも効く
（[ガードと機密](guard-and-sensitive-data.md)）。
